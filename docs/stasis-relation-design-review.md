# 铜球扣牌关系：交给 GPT-6 Pro 的设计审阅材料

日期：2026-09-13。状态：方案讨论，用户要求暂停铜球关系实现。本文件不代表用户批准修改注意力、增加关系token或新增关联特征。stasis区域已获批准，但具体关系方案待审。

## 1. 请审阅什么

我们在做STS1 Ironclad单场战斗强化学习，目标是理解并实践统一实体Set Transformer。请比较下面的关系输入方案，推荐满足需求的最小实现，指出必要信息、可能的信息泄露、置换等变性、动作头/价值头接入和测试边界。不要默认注意力偏置是最终答案，也不要把更复杂的图网络当作必选项。请区分代码已实现、后端诊断事实、尚未核实的游戏公开信息及设计推断。

## 2. 已确认的任务边界

- 一张实际卡牌一个CARD token、一个敌人一个ENEMY token、一瓶药水一个POTION token、一件遗物一个RELIC token；玩家与全局信息合成一个PLAYER token。
- 每类特征分别投影至同一宽度，再进入同一个可堆叠自注意力模块。实体数量动态，批次补齐使用有效性mask。
- token不使用槽位、内部实例号或随机seed等身份数值。稳定引用只用于连接实体和动作路由，不能作为连续值或身份embedding供模型记忆。
- 模型目前只处理当前决策时刻的实体集合，没有跨时间Transformer或RNN记忆。
- 所有卡牌选择、候选动作和自动/重复出牌上下文复用共享接口。不建立第二套选择协议，不自动替玩家做选择。
- 模型学习固定游戏规则，不给策略标签。输入可包含玩家可见的当前状态和必要的公开历史，不输入隐藏RNG、后台队列或未公开未来行动。
- 卡牌region新增stasis已获用户批准。奖励仍battle_reward_v1，不因本设计新增辅助奖励。不做PPO正式训练，不实现下一场战斗。
- 用户希望实现简洁，不为极端容量案例做专门工程。

## 3. 具体问题与证据级别

锁定后端7476a81954020087da31d41d16fddf475746ec2d中，铜制机械人偶spawnBronzeOrbs创建两只铜球，位于内部槽0和2。内部槽仅用于说明源码，不可进入模型语义。

C组A0诊断实际观察：第一次结束回合后出现两只铜球；随后两个后端stasis槽分别保存Bludgeon和Immolate，这两张牌离开公开四牌区；击杀持牌铜球后，相应扣押槽清空并发生卡牌返还。这证明后端存在一对一持牌关系，不等于已完成所有返还分支或正版UI可见性核验。

尚需核实的公开信息：玩家在扣牌期间是否可确定每只铜球具体持有的卡牌身份、升级和哪些实例动态属性。不能因为诊断能读到完整CardInstance就自动全部导出。应复用已批准的卡牌可见性规则；不可见的即时费用保持unknown，不把值填0冒充已知。

示例：铜球A当前HP=12，铜球B当前HP=20；重锤和防御都在stasis。如果只提供两个敌人token及两个stasis卡token，交换两只铜球持有的卡牌后，模型输入实体集合可能完全相同，但玩家希望取回的卡对应不同目标。这是一个结构性信息缺口的示意，不是已经采集证明可达的成对真实场景。

需求不是额外告诉模型“杀A更好”，而是让它知道“这张卡与A关联”。是否值得杀A由策略学习。

## 4. 当前共享模型真实结构

全卡实现提交1dc281d，最终报告提交2325d55；接口unified-entity-interface-v4，模型unified-entity-set-v4，普通CARD115维。读取的是本地共享任务源码，未修改该任务。

默认宽度64、4头、2层、前馈128、dropout0。每类特征线性投影，并加实体类型embedding。没有全局位置编码。

当前注意力核心：

```python
qkv = qkv_projection(layer_norm(x))
q, k, v = split_into_heads(qkv)
logits = q @ k.transpose(-1, -2) / sqrt(head_dim)
logits = logits.masked_fill(~entity_valid[:, None, None, :], -inf)
attended = softmax(logits, dim=-1) @ v
x = x + output_projection(attended)
x = x + feed_forward(layer_norm(x))
x = x.masked_fill(~entity_valid[..., None], 0)
```

最终有效实体均值作为context。动作头输入：源实体向量、目标实体向量、context、动作类别embedding、源/目标是否存在标志、公开结算上下文。价值头输入context和同一公开结算上下文。

```text
action_score = MLP([source, target, mean_entities, action_kind,
                    source_present, target_present, public_resolution_context])
value = MLP([mean_entities, public_resolution_context])
```

关键核实：EntitySample有edges成员，但当前形状是[N,N,0]；collate严格检查零维关系特征；EntityBlock.forward只接收x和valid，不读取edges。也就是说，“关系管道已经可用”是错误说法。任何非零关系输入都需改编码/批次契约；注意力方案还需改模型forward和版本。

当前保留edges占位可能便于未来扩展，但不应仅因有这个名字就选择关系注意力。

## 5. 所有方案共同的最小环境关系

假如公开可见性核验支持，应导出概念上的：

```json
{
  "relation_type": "holds_card",
  "source_ref": "opaque-enemy-reference",
  "target_ref": "opaque-card-reference"
}
```

这只是讨论中的结构，不是已实现schema。引用用于对齐两个当前实体。模型看关系类别和关联的实体语义，不把引用字符串编码进去。

生命周期要求：
- 扣牌完成后的可观察点：卡从原区域移到stasis，保留其真实实例身份，建立关系。
- 持牌铜球移除、返还动作完成后的可观察点：删除关系，卡进入实际返还区域；具体返还区域按游戏机制，不预设永远进手牌。
- 若战斗结束或特殊清理，依后端完整结算后生成最终观测，不能留下悬空关联。
- 同槽同名新铜球是新实例，旧引用不可命中新铜球。铜球HP变化和实体排序变化不能破坏关系。
- 关系不是合法动作。stasis卡不因为有token就变成可打出/可选择；动作仍由环境mask决定。
- 不预先发放“将返还哪张牌”的隐藏未来信息：关系只表达当前已公开的持有事实。

## 6. 方案A：有向关系的注意力偏置（之前提出，未实施）

建立两种有向类别：enemy_holds_card、card_held_by_enemy。无关系的偏置固定为0。对于第l层第h头：

```text
score[l,h,i,j] = dot(Q[l,h,i], K[l,h,j]) / sqrt(d)
                 + bias[l,h,relation(i,j)]
```

当前holds_card关系产生两条方向边，以便敌人关注所持卡，卡关注持有敌人。每方向每头每层一个标量参数；若层间不共享，两层四头两方向共16个新增偏置参数。是否共享层参数是可选实现，不影响环境关系的定义。

随后仍执行原实体有效性mask和softmax，不把关系当作强制注意力，也不屏蔽无关实体。bias可从0初始化，这样刚加载时尽可能保留原注意力计算；零初始化不代表训练后一定有效，也不代表旧checkpoint能精确续训。

路径：关联影响敌人/卡牌的上下文向量，动作头读取目标铜球向量，价值头读取实体均值。两头结构上都可能使用关系，不保证每一组权重或每一个样本必然输出差异。

置换：token顺序变为P时，关系矩阵同步变为P R P^T。实体输出应等变；对应动作对齐后的分数和全局value应不变。只重排token而不重排边会选错目标。

代价：改EntitySample/encode/collate、模型注意力签名、checkpoint/契约版本、测试。实现为稠密矩阵时，额外关系存储随N平方增长；边很稀疏，可保存边列表再在既有attention分数上索引加偏置。现有attention本身仍是稠密，不能因此宣称整个模型稀疏。

局限：只有标量bias，改变的是“关注谁”，并不直接把扣牌语义强制注入目标表示；需要训练学会使用。实体特征完全相同的对称场景未必需要被区分，也不应靠slot打破对称。该方案可推广到其它公开关系，但本任务不应借机预建无关关系系统。

## 7. 方案B：关系驱动的一次特征融合

用同样环境边，在自注意力前对持牌敌人的初始向量加入被扣卡的投影。例如：

```text
z_enemy = base_enemy + W_holds * z_held_card
```

没有持牌关系时增量为0；卡仍保留单独token，不复制成第二个CARD实体。若每个铜球最多持一张牌，这个gather很简单；多张情形必须先核实是否需要，不预建泛化池。

优点：无需改变每层attention；直接将关联卡语义接入敌人表示；动作和价值通过现有实体路径使用。正确按引用gather同样支持置换等变。

代价：需新融合模块/参数和版本；原本“每类独立编码后共同attention”的前处理增加跨实体依赖。要说明是否双向融合，避免把关系是否存在含混地藏在一次数值相加中。若一次加入后信号被忽略，仍需要训练，不能保证优于A。

请比较B是否比A更符合“只有一个机制需要关系时的最小工程”，而不是因为A参数少就默认A更简单。

## 8. 方案C：只向候选动作加入扣牌上下文

对攻击铜球的候选，给动作头附加所持卡的语义或编码向量。能直接影响选哪个铜球，但价值头原输入看不到关联；若采用，还需要把公开关联信息汇总给value。

局限：AOE、无目标技能、药水、选牌阶段也可能受“哪只怪扣哪张牌”影响。只给直接攻击候选可能漏掉这些决策；维护多个特殊候选分支可能比A/B更复杂。不能重复之前“动作头有信息、价值头没有”的问题。

## 9. 方案D：新增关系token

增加一个关系实体并连接两个端点。仅放一个holds_card类别token、没有端点绑定，不能表达谁持有谁。若关系token内拼接两端语义，可能复制语义且对完全同名但属性不同的实例绑定仍需明确。

增加第六类实体会改变当前五类统一契约，且没有消除稳定关联需求。本项目暂不推荐，但请说明在什么条件下它反而更合适。

## 10. 不建议的简化

- 把“铜球槽0/槽2”当作卡牌数值特征：依赖槽位与排序，违背现有边界。
- 只加region=stasis而不关联铜球：知道扣了哪些牌，不一定知道攻击谁能拿回哪张。
- 只记录环境JSON关系但模型不读取：后端信息齐全不等于策略观测到。
- 给铜球写“先杀优先级”或返还卡收益分数：把策略或奖励推导写进输入。
- 直接把扣牌放resolving并取消NORMAL校验：改变已有流程语义；用户已经批准独立stasis区域，无需这样绕过。

## 12. 建议的验收而非预设通过

- 真实两铜球分别扣牌、逐个返还；手牌满等正常边界按现有机制核查，避免假设返还固定区域。
- 交换实体顺序并同步关系/动作路由，动作对应目标不变；padding不能制造关系或污染value。
- 缺失端点、过期引用、重复不一致关系明确拒绝，不静默丢弃。
- 人工固定实体语义，只交换两只属性不同铜球的持牌关系，使用有判别力的受控权重验证关系可影响actor和critic；随机初始化输出恰巧接近不能当成无通路。
- 关系参数或融合通路有梯度；无关系场景按所选初始化策略与旧网络对照。
- 保持现有训练异常/截断语义，版本和指纹拒绝不兼容checkpoint。新结构的精确恢复另做短诊断，不将旧模型加载称为精确恢复。
