# A-First Battle Initial-State Dataset Plan

**Date:** 2026-09-19  
**Status:** Current plan for initial-state dataset preparation  
**Project:** `Sunsh1neY/sts1-SetTransformer-PPO`

## 1. Current decision

The battle backend, combat state representation and policy-facing Token path are now treated as ready for the next data stage.

The canonical combat-entry state is frozen by `battle-initial-state-v1`:

> A battle initial state is the complete **pre-combat initialization** state that is already determined, can affect future combat, and cannot be derived unambiguously from other stored fields. Stochastic realization is generated by the backend from the initial state plus an independent environment seed.

The dataset strategy is now changed from “prepare A and B together” to:

```text
Reconstruct A as completely as practical
        ↓
Measure actual reachable-state coverage
        ↓
Identify important holes
        ↓
Decide whether B is needed
        ↓
If needed, add only targeted reachable B states
```

No A/B mixture ratio is decided in advance.

---

## 2. Research goal of this stage

The immediate goal is not to maximize the number of initial states.

The goal is to answer:

1. What combat initial states can be reconstructed from real run records under the current backend and current schema?
2. How broad is the resulting coverage of decks, HP, relics, relic state, potions, encounters and important mechanic interactions?
3. Which important states or mechanisms remain poorly covered?
4. Is the reconstructed A corpus already sufficient for the planned PPO experiment?
5. If not, what is the **smallest justified set of reachable constructed B states** needed to close the important gaps?

The B corpus is therefore a response to measured A-coverage gaps, not a precommitted second dataset of arbitrary size.

## 4. Source strategy

## A — verified real-record reconstruction

A states come from real run records.

For each candidate combat, reconstruct the canonical `pre_combat_initialization` state as far as the source and game rules permit.

The reconstructed state may include:

- character / ascension / act / floor;
- HP / max HP;
- complete master deck and upgrades;
- required permanent per-card state;
- relic ownership;
- required persistent relic state;
- exact relic-card bindings when required;
- potion inventory;
- encounter;
- burning-elite state where required.

A state is admitted only when every state component required by the current simulator can be established without guessing.

New backend randomness is allowed after reset. Therefore A means:

> verified reconstruction of the **battle-entry state**, not exact replay of the historical battle realization.

---

## 5. Primary data source and tools

The main reconstruction workflow should use:

- Codex for repository-aware extraction, reconstruction logic, tests and reports;
- available `.run` / run-history files;
- existing public-corpus extraction and provenance code where still useful;
- `SlayTheData.7z` or other already identified run corpora when practical;
- current backend/registry/schema as the admission authority.

Historical data work is reusable as evidence and tooling, but its old admission counts are not current conclusions.

Earlier work recorded, under older backend limitations:

- 157 independent Ironclad run groups;
- 3,957 combat records;
- 1,282 audited Act 1 floor 1–15 combat records;
- 257 rule-constructible candidates across 118 runs;
- 160 distinct deck multisets.

Those numbers describe the historical audit only. The current backend has materially broader card, enemy, potion and relic support, so the reconstruction must be rerun against the current implementation.

## 6. Reconstruction pipeline

### Phase A0 — freeze the reconstruction contract

Use `battle-initial-state-v1` as the target schema.

Before bulk reconstruction, Codex should verify that the current runtime can consume or losslessly adapt all required schema components:

```text
run record
   ↓
historical prefix reconstruction
   ↓
battle-initial-state-v1
   ↓
current reset adapter
   ↓
C++ backend
   ↓
first policy observation
```

The schema itself is not reopened merely because the source format differs. Source-specific data is converted into the canonical schema.

### Phase A1 — inventory source records

Build a machine-readable inventory containing at least:

- raw source path;
- raw source hash;
- run identity / connected source group;
- character;
- ascension;
- source build/version when available;
- combat floors;
- available reconstruction fields;
- missing-field reasons.

Deduplicate identical or related copies before counting coverage.

One run may contribute multiple combat initial states, but all states derived from the same run remain linked to the same source group.

### Phase A2 — reconstruct the historical run prefix

For every combat candidate, reconstruct the state immediately before that combat.

Apply only source-backed and rule-backed historical transitions needed to establish:

- deck changes;
- upgrades;
- permanent per-card values;
- HP/max-HP changes;
- relic acquisition/replacement;
- persistent relic counters/state;
- relic-card bindings;
- potion acquisition/use/discard;
- act/floor progression;
- encounter identity;
- burning-elite information where applicable.

If a required historical transition cannot be established, do not silently continue with guessed values.

Record the first unresolved dependency and the exact reason.

### Phase A3 — canonicalize into `battle-initial-state-v1`

Convert every reconstructible candidate into the frozen semantic schema.

Important rules:

- master deck semantics are unordered unless an exact entity relation requires concrete instance identity;
- local refs are routing identifiers, not policy features;
- environment seed is not part of initial-state identity;
- hidden draw order and hidden future enemy moves are not reconstructed;
- start-of-combat effects are not pre-applied;
- derivable fields are not redundantly stored;
- dataset provenance stays outside game state.

### Phase A4 — current-backend admission

Every A candidate must be tested against the **current** backend and current registries.

Admission checks include:

- all cards and upgrades supported;
- required permanent card state supported;
- all relics supported;
- required relic persistent state available;
- required relic-card relations recoverable;
- potions supported;
- encounter supported;
- act/floor/ascension combination valid;
- no unsupported selection/generation closure;
- reset succeeds;
- first observation is valid;
- Token encoding succeeds;
- entity/resource bounds are respected;
- legal action set is nonempty;
- representative rollouts do not fail because of missing state.

A historical state is rejected intact if one required component is unsupported or unknown. Do not remove the offending component and relabel the remainder as the same A state.

### Phase A5 — provenance-safe split

Split at source-group level before training use.

Related states from one run must not cross train/development/evaluation boundaries.

The exact final split policy can reuse existing connected-source grouping if still valid, but must be recomputed on the final A inventory.

Multiple environment seeds applied to one state do not create new independent source states.

## 7. A-corpus coverage analysis

Before any substantial B construction, produce a coverage report for the admitted A corpus.

### 7.1 Basic distribution

Report at least:

- independent source runs;
- admitted combat states;
- rejected states and reason counts;
- Act 1 / Act 2 distribution;
- floor distribution;
- normal / elite / boss / event-combat distribution;
- deck-size distribution;
- HP/max-HP and HP-ratio distribution;
- potion occupancy and identities;
- relic count and identities;
- relic persistent-state distributions.

### 7.2 Card and deck coverage

Report:

- card identity frequency;
- upgrade frequency;
- duplicate-copy frequency;
- important archetype/mechanic families;
- full-deck content diversity;
- rare cards;
- cards absent from admitted A states;
- important card pairs / triples with insufficient support.

Coverage is about distinct initial states and source groups, not the number of environment-seed replays.

### 7.3 Relic coverage

Report:

- each admitted relic's occurrence count;
- relic combinations;
- persistent counter values;
- threshold-near counter coverage;
- Bottled-style relations;
- information-visibility relics;
- interactions between relics and cards/enemies/potions.

For cyclic or threshold relics, frequency alone is insufficient. Explicitly inspect whether decision-important states are represented, such as values immediately before a trigger.

### 7.4 Encounter coverage

Report:

- encounter identity frequency;
- deck × encounter coverage;
- relic × encounter coverage;
- important matchup holes;
- whether some decks appear only against a narrow subset of enemies due to source-history correlation.

### 7.5 Mechanic-interaction coverage

Maintain a small explicit interaction matrix for important mechanisms already implemented in the environment.

Examples include, where applicable:

- strength source × strength payoff;
- exhaust source × exhaust payoff;
- status generation × status payoff;
- retained-hand / cost-changing interactions;
- relic threshold × high-value card choice;
- Bottled relation × bound-card behavior;
- Frozen Eye × draw-order decisions;
- Runic Dome × intent-hidden decisions;
- potion availability × relevant encounter state.

The purpose is not to enumerate every combinatorial pair. It is to identify meaningful mechanics that the agent may otherwise rarely experience.

## 8. Decision gate before B

After the A coverage report, explicitly choose one of the following outcomes.

### Outcome A — A is sufficient

If A provides broad enough state and mechanism coverage for the intended experiment:

```text
A only
→ define sampling distribution
→ freeze train/dev/eval pool
→ short integration run
→ formal PPO experiment
```

No B corpus is required merely because B was discussed earlier.

### Outcome B — A is mostly sufficient

If A is broad but has a small number of important holes:

```text
A
+
small targeted B supplement
```

This is currently the preferred fallback.

Examples:

- a rare supported card never appears in admitted A states;
- an important card combination appears too few times;
- a relic counter almost never appears near its trigger threshold;
- a supported encounter is absent or severely underrepresented;
- a key card/relic interaction is technically supported but effectively unseen.

### Outcome C — A is structurally insufficient

Only if the A audit shows large systematic gaps should a broader B-construction system be designed.

Examples:

- whole important mechanic families are absent;
- source records cannot reconstruct required persistent relic state for a large fraction of states;
- encounter/deck correlations make broad combat learning impossible;
- admitted A volume is too small after strict reconstruction.

A comprehensive B generator is therefore conditional, not assumed.

---

## 9. B policy if supplementation is required

The detailed B construction rules are intentionally deferred until the A report exists.

The already accepted direction is:

> B may modify Deck, HP/max HP, Relic, persistent Relic state, Potion, Encounter and, when needed for reachability, Act/Floor — but the resulting state must remain rule-valid and reachable by some legal Ironclad run prefix.

B does not require reconstructing that prefix.

However, B should be introduced only for concrete measured gaps.

Every B state must record:

- construction purpose;
- gap being addressed;
- fields changed from any source reference, if a source reference is used;
- reachability rationale;
- whether it is a coverage, threshold, interaction or matchup state.

Do not create a large Cartesian product of all cards × relics × HP × encounters.

---

## 10. Sampling is a later decision

Corpus membership and PPO sampling probability are separate problems.

Do not decide the final training distribution merely by counting A states.

After A and any justified B supplement are frozen, separately design:

```text
initial-state-corpus-v1
        ↓
training-distribution-v1
```

The sampling policy should prevent high-frequency source patterns from automatically dominating training while still reflecting the intended research task.

This decision comes after the corpus coverage report.

## 12. Acceptance criteria for the A stage

The A stage is complete when:

1. the current run corpus has been re-audited against the current backend rather than old support assumptions;
2. every admitted state conforms to `battle-initial-state-v1`;
3. every admitted state's required fields are source/rule supported rather than guessed;
4. every admitted state can reset through the current backend and reach a valid policy observation;
5. source groups are deduplicated and leakage-safe;
6. rejection reasons are explicit;
7. coverage is reported by meaningful semantic dimensions rather than only total scene count;
8. important missing mechanisms/interactions are listed;
9. there is enough evidence to decide whether B is unnecessary, small and targeted, or broad.

There is no minimum arbitrary A-state count in advance.

## 14. Governing principle

> First measure the real reachable state space that can actually be reconstructed from run records under the current implementation. Do not build a large synthetic corpus before knowing what is missing. Use B only to repair demonstrated coverage gaps, with the smallest construction scope that makes the experiment complete enough to answer its research question.
