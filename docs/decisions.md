### D14 RNG 实现：主流 xorshift128+，洗牌临时 Java LCG（2026-09-03 初裁，2026-09-05 正式修订）

- 原裁定纠正：2026-09-03 将战斗全部随机性写成 `java.util.Random`，范围判断错误。当前实现早已区分双层 RNG，但当时未同步决策日志；本次才正式登记，不能把代码注释中的“已登记”当作过去发生的记录。
- 当前后端：`sts::Random` 使用经 murmurHash3 初始化的 xorshift128+；洗牌消耗 `shuffleRng.randomLong()` 产生种子，构造临时 Java 48 位 LCG 执行洗牌。Python 教学实现对应为 `StsRandom` 与 `JavaRandom`。
- 初始化：`BattleContext::init` 中 `aiRng`、`monsterHpRng`、`shuffleRng`、`cardRandomRng` 由 `Random(run_seed + floor_num)` 的同一初始状态复制；`miscRng`、`potionRng` 继承整局 `GameContext` 状态。不能写成“层数不进入 RNG”或“全部流重置”。

### D17 动作头：保留实体对应关系，逐个候选动作打分（2026-09-05，项目审核后用户确认）

- 裁定：Set Transformer 保留每张手牌和每个敌人的独立编码；动作头结合局势信息，对每个“牌—目标”候选动作打分，再按当前槽位、目标索引排列为原有离散动作 logits。结束回合单独打分，全部 logits 合并后统一施加合法动作掩码并做 softmax。
- 编码边界：槽位号不进入 token 特征；实体与输出编号的对应关系由数据排列维护。无目标卡仍只使用目标 0（mechanics.md §5），不产生重复动作。
- PMA 用途：全局池化结果用于价值估计及局势上下文；动作选择同时读取未池化的实体编码。
- B 阶段：DT 的序列仍为 `(R_t, s_t, a_t)`，动作仍是一个离散 token；预测 `a_t` 时，动作头同时读取当前手牌、目标的实体编码及截至 `s_t` 的因果上下文，不能仅凭池化后的状态摘要预测槽位。
- 理由：手牌 `[Bash, Strike]` 与 `[Strike, Bash]` 在其余状态相同、两牌均合法时拥有相同集合摘要和合法掩码，但“打 Bash”的动作编号不同；只用摘要的固定输出头无法区分。该结论由规格内的换位反例推导，不依赖游戏数值或论文性能主张。
- 验收：仅重排手牌或敌人并同步重排相应 mask 后，动作分数和概率应随对应实体重排，结束回合分数及全局价值保持不变。此为模型阶段待实现的验收要求，本次仅登记设计。
- 推翻条件：替代方案能够保留上述对应关系、通过换位验收并遵守 D5 的离散动作和 mask 约定；须先登记理由与证据。具体评分函数留到模型阶段确定。

### D18 最终成绩：失败同分，胜利按剩余血量加分（2026-09-05，用户确认）

- 历史状态：本条继续作为独立战斗目标的来源；D27 将“win”限定为 `battle_won`，完整爬塔的 `run_won` 另用稀疏 0/1 奖励，禁止混用。
- 裁定：整场最终成绩 `R = win * (1 + λ * HP_remaining / HP_max)`。正常失败与硬超时判负均为 0，不因对敌伤害、剩余敌方血量或拖延回合而获得不同的最终成绩；胜利仍按 D7 的 λ 约定加剩余血量分。
- 理由：用户确认“把敌人打到残血后失败”和“几乎未造成伤害就失败”应同分；训练目标与最终评价均围绕获胜及获胜时的剩余血量。
- 奖励口径：最终成绩 `R`、逐步奖励 `r_t`、累计回报 `G_t` 分别定义。A/B 共享逐步奖励及回报累计口径；从一场战斗起点累计的回报须与 `R` 一致，不能在辅助反馈中重新引入不同的失败成绩。
- 辅助反馈边界：按 D20，当前直接发放终局奖励、γ=1，不实现势能反馈，U8 基础版本已明确。未来若需要势能反馈，须另行定义初始与终止势能、累计方式及自举规则；单步公式应为 `γ * Φ(next) - Φ(current)`，且必须证明累计回报仍符合本裁定。
- 验收：不同初态、伤害量、持续步数的失败与硬超时轨迹最终均为 0；胜利累计回报符合上述公式；A/B 对同一奖励序列计算一致。具体实现的测试结果单独记录，文档裁定不视为已通过验收。

### D23 Agent 决策与环境执行分层（2026-09-05，T4 用户审计后修正）

- 裁定：正式 Agent 统一通过 `decide(observation)` 返回 `AgentDecision`，其中包含掩码后的 `probabilities: float64[31]` 与本次已选的原动作编号 `action: int`。概率表示抽样前的策略分布；整数表示已经发生的单次抽样结果，两者不得混称或互相替代。用户复核后确认 one-hot 与整数表达同一个离散动作，接口直接使用更紧凑的整数，不传冗余 one-hot。
- 随机 Agent：以全零 logits 调用同一 `masked_softmax`，得到合法动作上的均匀概率；随机抽样由 Agent 自己持有的独立 RNG 完成，随后返回所选整数。未来模型 Agent 也在自身边界内根据掩码后分布作出决策并保留训练所需概率或 log-prob。
- 接入层：通用 episode runner 只调用 Agent、严格校验所选整数属于 0–30 且在该策略分布中概率大于 0，再原样交给环境；不持有 RNG，不读取卡牌、能量或敌人字段，不重算合法性。环境只负责 `reset/step` 与产生下一观测，Agent 与具体 wrapper 可互换。
- 终局：runner 根据环境返回的 `terminated/truncated` 停止，不在终局再次调用 Agent。非终局全非法由 Agent 的 masked softmax 显式报错；终局观测全 False 由环境契约测试验证。
- 理由：T4 初版 `MaskedRandomPolicy.act()` 直接返回整数且自身包含 `run_episode()`，把 Agent 决策、动作表示和环境控制流揉在一个类中；未来输出 31 维分布的模型无法无缝替换，且 masked softmax 没有进入随机 Agent 的真实路径。用户审计指出该耦合后，本决策取代 T4 初版接口，不改变 D17 的动作编号或 D19 的信息边界。
- 验收：随机 Agent 的 31 维概率 shape/dtype/归一化正确，返回的整数动作必须属于环境 mask；runner 不含 RNG 且能用同一接口驱动 FlattenWrapper、TokenWrapper 与测试 Agent；两条正式 wrapper 路径均跑到终局并逐步核对后端实际收到的动作。
- 推翻条件：若 PPO/DT 框架要求返回包含 action、log-prob、value 等更丰富的批量对象，可扩充 `AgentDecision`，但必须保留“Agent 内完成选择、runner 不重算合法性和不二次随机”的边界，并先登记迁移方案。
