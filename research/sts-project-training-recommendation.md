# STS 战斗 Agent 的状态分布、动作协议与 3060 训练路线

状态：研究完成
检索日期：2026-09-13
项目依据：当前工作区的 spec-v6、M2/M3 报告和训练报告

## 60 秒结论

你当前的 STS 项目已经不处于“没有训练数据、只能重新设计架构”的阶段。更准确的描述是：

- 固定的 comparison-battle-v2 已经完成了 MLP/Set 的 GPU 对照；
- public-battle-v1 已经有 66 位动作协议、公开派生场景和规则 Agent；
- 公开 corpus 已经筛出大量候选入口；
- 但 public 观测到新模型的迁移、正式准入、自然分布代表性和更大范围 PPO 仍要单独验收。

所以当前最优路线是：

固定 public battle 契约 → 完成 66 位观测到 Set 的迁移 → 用规则/公开前缀入口生成器提供自然战斗初态 → 做从头 PPO 短诊断 → 再扩展状态分布 → 最后才做 RunEnv 和 decision Agent。

不要为了“找到更多战斗状态”立刻训练一个 decision Agent。它不会给你一个中性的状态采样器；它会给你一个由自身奖励、策略偏差和当前 battle Agent 能力共同决定的状态分布。

## 1. 当前项目状态：问题不是“零数据”

### 1.1 动作协议已经分成两个版本

当前工作区同时保留两个有意不兼容的任务：

- minimal-v1：旧的 31 位动作，10 个手牌槽位 × 3 个目标列 + 结束回合；
- public-battle-v1：10 个手牌槽位 × 5 个目标、结束回合、3 个预留药水槽 × 5 个目标，共 66 位。

public-battle-v1 的 3 个药水槽是容量预留，A20 实际只有 2 个药水槽。public 新观测不能直接喂给旧 31 位 MLP、旧 TokenWrapper 或旧 checkpoint；新动作、观测、序列化和模型头必须作为新版本联合迁移。[P01][P02]

这意味着“动作空间可能太大”目前应拆成两个问题：

1. 66 个直接动作是否让 PPO 难以训练；
2. 未来二次选择、复制、生成和牌堆对象是否无法用 66 个直接动作表达。

第一个问题目前没有证据表明是主瓶颈；第二个问题已经被项目规格明确列为需要 selection phase、候选动作和容量审计的边界。

### 1.2 公开状态候选已经存在，但还不是正式训练集

M2 corpus 报告记录了：

- 固定仓库中 203 个 Ironclad 原始文件；
- 157 个关联 run 组；
- 第一幕第 1–15 层审计 1,282 场战斗；
- 257 个按已核实规则可构造、但来源完整规则尚未认证的候选场景；
- 190/46/21 的研究预划分；
- 正式准入场景仍为 0。

这不是“没有状态”，而是“状态尚未通过正式来源、内容闭包、动作表达、容量和后端准入”。候选数量不能直接写成训练样本数量，也不能把同一来源组多次重采样当成新的玩家经验。[P03]

### 1.3 当前 public 环境已经能运行，但学习管线身份不同

public-battle-implementation 报告记录：

- 99 个公开派生完整内容场景、75 个关联 run；
- 35 类 Ironclad 牌、5 张辅助牌、8 个遗物、15 个直接药水；
- 66 位规则/随机 Agent 接口；
- 修复后二进制上 99 场真实派生场景规则和随机策略均自然结束；
- 完整仓库回归 566 项通过；
- public 观测到 MLP/Set 的模型和轨迹迁移、扩展环境从头 PPO 短诊断仍未完成。

因此，99 场是工程闭环证据，不是总体玩家分布，也不是 public Set-PPO 已经训练完成的证据。[P04]

## 2. 你的三个问题分别应该怎么处理

### 2.1 动作空间：保留 66 位直接动作，二次选择单独建 phase

当前不建议把 66 位再改成一个更复杂的通用分层策略。建议如下：

| 决策类型 | 推荐表示 | 原因 |
|---|---|---|
| 出一张手牌并作用于敌人 | 固定 action schema 中的 hand_slot × target | 数量有限，mask 和 replay 映射容易验证 |
| 直接使用药水并作用于敌人 | 固定 potion_slot × target | 与现有 public 契约一致 |
| 结束回合 | 独立动作 | 没有来源/目标依赖 |
| 从手牌、抽牌堆或弃牌堆选择一张牌 | selection phase + 动态候选列表 | 不把牌堆 × 卡牌 × 目标乘入全局动作头 |
| 选择多张牌或执行复制/生成 | 明确选择数量规则 + 候选实体 | 防止自动代选掩盖动作表达缺口 |
| 复杂长程战斗规划 | 后续 candidate scorer 或搜索/规划混合 | 不是简单增加 logits 就能解决 |

模型输入中的候选应该只包含当前公开的实体语义、区域、费用、目标类别和选择上下文。候选索引可以回到环境对象，但不能让 unique ID、隐藏队列、真实抽牌顺序或未来结果进入 token。

动作协议方面，最重要的不是减少 66 这个数字，而是保证以下等式一直成立：

环境合法动作集合 = Agent 看到的合法动作集合 = PPO 重新计算旧动作概率时使用的合法动作集合。

### 2.2 状态样本：先做入口采样器，不做 decision Agent

建议把状态生成器命名为 battle-entry sampler，而不是 decision Agent。它的任务只是按版本化政策选择合法的战斗入口，不学习整局价值。

第一版可以包含三个来源：

#### 来源 A：标准自然入口

从锁定的标准 reset 开始，使用固定遭遇和规则环境产生战斗。它的优点是完全在线、最容易解释，缺点是中途卡组和药水覆盖有限。

#### 来源 B：公开 run-derived 入口

从公开 run 里抽取完整卡组、已升级牌、HP、楼层、遭遇、遗物和药水，在已经审计的规则下重新初始化战斗。未知牌、未支持遗物、二次选择、动态生成或容量不能证明时，整场拒绝。

这类入口是“真实卡组驱动的规则派生战斗”，不是原局精确回放。公开文件的 source seed 用于来源关联和分组，环境 seed 另行分配，不进入模型观测。

#### 来源 C：机制诊断入口

用于测试某张牌、某个敌人机制、某个选择阶段或容量边界。它不参与自然分布的总体胜率，除非被明确标记为一个独立 task_spec_id。

### 2.3 公开 .run：能用，但用途不是你最初想的那种

推荐使用方式：

1. 用 .run 做卡组、升级、路线、药水和遗物覆盖统计；
2. 按关联 run group 做来源划分，避免同一局不同副本泄漏到 train/dev/eval；
3. 对字段足够的前缀重建 battle entry A；
4. 对缺失的牌堆顺序、敌方内部随机性和跨战斗 RNG 采用独立重采样；
5. 训练 PPO 时让环境生成真实 transition，而不是直接把 .run 的最终字段转成动作标签；
6. 只有另行采集逐步 observation-action-reward 时，才把数据交给 DT 或 BC。

你当前 M2 报告已经验证了这个方向的边界：公开 corpus 可以形成 257 个规则候选，但正式准入为 0；研究预划分不等于正式训练或保留评估。[P03]

## 3. decision Agent 是否应该现在实现

### 3.1 现在实现的收益

它可能带来：

- 更丰富的中途卡组；
- 更真实的选卡、路线和资源组合；
- 将来能够训练 run-level policy；
- 为 DT 提供整局高层轨迹。

### 3.2 现在实现的成本

它同时要求：

- 完整 RunEnv；
- 地图、事件、商店、篝火、奖励和资源状态；
- run_reward_v1 的成功定义；
- 高层 action schema；
- 战斗结束如何回写 RunEnv；
- 跨战斗 RNG、遗物、药水和牌组变化；
- 高层选择的 credit assignment；
- 用什么策略生成训练数据，以及它是否会被 battle Agent 的能力反向影响。

这已经是项目的另一阶段，不是一个“给 battle PPO 找 reset 状态”的小工具。当前规格也明确区分 battle_reward_v1 和 run_reward_v1，未实现完整 RunEnv 时不能把独立战斗奖励解释成整局通关奖励。[P05]

### 3.3 推荐的未来顺序

战斗 Agent 稳定后，再按以下顺序做：

1. 先实现 RunEnv 的规则转移，但使用固定随机/规则高层策略；
2. 记录每个高层决策前的公开状态、候选、选择和后续结果；
3. 先用这些轨迹做统计和 BC/DT 数据质量审计；
4. 用稳定的 battle Agent 作为下游执行器；
5. 最后再训练 decision Agent，并将 run reward 与 battle reward 分开。

## 4. 3060 训练和评测方案

### 4.1 已有 GPU 证据说明硬件不是当前主阻塞

comparison-ppo-report 记录的固定范围实验为：

- RTX 3060 Laptop GPU；
- MLP/Set 各 2 组；
- 每组 70,656 transition；
- 总训练与评估耗时 1,097.41 秒；
- MLP 381,150 参数，Set 140,222 参数；
- 633 项 CPU 回归和 15 项 CUDA 相关测试通过；
- 四组相对初始策略的开发配对改善区间下界均大于 0；
- Set−MLP 区间包含 0，因此没有架构优势结论。

这证明在已冻结的环境和模型规模内，3060 可以完成工程级短训练。它不证明 public 扩展环境、全卡组合或更长训练一定可行，但已经足以否定“必须先换显卡才能继续”的判断。[P06]

### 4.2 对 public Set 的实际训练顺序

第一步不是扩大模型，而是完成迁移和短诊断：

1. 统一 public observation schema、action_schema=2、registry、容量和 reward metadata；
2. 将逐牌实体、玩家全局实体、敌人、药水和遗物接到新 Set 编码器；
3. 逐候选生成 hand-target、potion-target、end-turn logits；
4. 在 softmax 前使用后端 action mask；
5. 检查手牌和敌人换位时，候选对应关系同步换位；
6. 用少量从头 PPO 检查训练、checkpoint 恢复和终止语义；
7. 再增加公开入口的数量和难度。

当前新统一实体配置已经登记为 64 维、4 头、4 层 SAB、PMA 摘要和动态候选评分。这个配置应当作为一次可复现实验，不应被写成“模型越大越好”的通用定律。[P07]

### 4.3 训练预算建议

建议每个明确范围做三类实验：

| 实验 | 目的 | 规模建议 |
|---|---|---|
| mask/接口短诊断 | 检查动作、终止、恢复和梯度路径 | 数千到数万 transition |
| 固定范围 PPO | 判断是否能从头学习 | 沿用项目预登记预算和多初始化 |
| 扩展分布 PPO | 判断状态覆盖变化的影响 | 只改变入口分布，保持 reward、gamma 和评估协议 |

不要在没有完成第一类诊断时直接启动长 PPO。出现学习停滞时，优先检查：

- 原观测和原 action mask 是否保存；
- PPO 旧 log-prob 是否使用动作发生时的 mask；
- terminated、truncated 和 reset 边界是否分开；
- battle_reward_v1 是否只在规定的首次胜利终局发放；
- value target、GAE 和 batch shape；
- 训练集是否只重复少数来源组。

### 4.4 评测必须按来源和自然分布分开

至少保留以下指标：

- battle_reward_v1；
- 胜率；
- 获胜条件下平均退出 HP 比例；
- 遭遇分桶；
- 卡组/药水/遗物分桶；
- 二次选择或药水目标动作的覆盖；
- 非法动作率；
- 外部截断率；
- 来源 run group 级别的 bootstrap 区间。

正式评估 seed 继续保持和训练 seed 隔离。公开来源组的 train/dev/reserved-eval 划分只能回答来源泛化问题，不能替代不可变环境评估 seed；同一个 run group 的不同战斗也不能被当作完全独立的玩家对局。

## 5. 一个可落地的入口采样器 v1

### 5.1 采样单位

不要以单个最终牌组作为采样单位。建议采样单位是：

scene = source run group + battle floor + encounter + complete deck/config + resampling policy

scene 之外的元数据进入日志，不进入模型观测。

### 5.2 训练采样起点

以下比例只是第一版工程假设，不是论文结论：

- 60%：均匀采样自然或规则派生入口；
- 20%：补足卡组、遭遇、药水和遗物稀疏桶；
- 20%：来自失败类型或学习潜力的受控重采样。

每次改变比例都记录 sampler_version，并在固定 eval 协议下比较。困难样本不能无限增加，否则训练分布会脱离真实入口分布。

### 5.3 入口验证

每次 reset 前检查：

- 牌组多重集和升级；
- hand/draw/discard/exhaust 的容量；
- 玩家 HP/max HP、能量和公开遗物；
- 药水库存和槽位政策；
- 敌人数量、目标索引、意图和 HP；
- 所有可能生成的状态牌、分裂和召唤；
- 当前 action mask 和 Agent 所见 mask；
- 环境 seed 与 source seed 分离；
- source/version/mod 兼容性；
- action schema、observation schema 和 reward version。

任何字段不足都拒绝该 scene，不用 PAD、0 或“自动选择”把缺口隐藏起来。

## 6. 现成先例对本项目的含义

### AlphaStar

Nature 2019 的 AlphaStar 是“结构化动作 + Transformer/实体表征 + 自回归动作头 + 人类 replay 监督初始化 + 联赛 RL”的先例。它证明复杂动作可以拆成有类型的条件参数，也证明大规模人类 replay 能帮助解决探索。但它使用的是顶级算力、海量 replay 和复杂基础设施；它没有证明个人笔记本可以复制相同训练结果。[S01][S02][S03][S06]

### MiniRTS

MiniRTS 是更接近“高层计划—低层执行”的先例：instructor 只生成高层指令，executor 将指令执行为低层动作；论文使用 7.6 万条人类指令—执行对，并在自定义 RTS 中验证层级表示。[S25]

它给你的启示是：如果将来要做 decision Agent，接口应当传递显式的高层目标或候选，而不是让高层 Agent 直接控制每一张战斗牌。但它不支持现在就同时训练两个未知策略。

### STS 公开项目

最接近你的公开项目是 Jialeiv/sts-rl-agent：小网络负责地图、选卡、商店、篝火和事件，战斗交给 MCTS；该项目还把多种战斗模仿、RL、注意力和价值前瞻尝试作为负结果公开。它的直接启示是“判断型非战斗决策”和“需要未来规划的战斗”可能需要不同计算模式。[S23][S24]

但它的结果证据是 50 个固定 seed、无置信区间的社区项目记录，且 README 自己说明部分评估早于规则补丁，不能把其数字当作 STS 战斗学习不可能的证明。

## 7. 最终执行裁决

### 现在做

1. public 66 位动作和新 Set 编码迁移；
2. selection phase 和候选动作接口；
3. battle-entry sampler v1；
4. 规则/随机自然入口和公开派生入口的来源分桶；
5. public Set 从头 PPO 短诊断；
6. 固定 seed、来源组和 action schema 的分层评估。

### 现在不做

1. 不把 decision Agent 当作 battle 状态随机生成器；
2. 不把 .run 直接转成战斗动作样本；
3. 不把 99 场工程集成写成总体分布；
4. 不把旧 31 位 checkpoint 迁移到新 66 位协议；
5. 不在扩展环境上继续拿旧 MLP 和新 Set 做架构优劣排名；
6. 不因为模型暂时不升分就盲目增大网络。

### 未来再做

当 battle Agent 在多个入口来源、多个遭遇和固定评估协议下稳定后，再实现：

RunEnv → 固定高层规则策略 → 完整高层轨迹 → decision Agent/DT。

这会让你的项目真正形成“高层整局决策—RunEnv—低层战斗 Agent”的闭环，同时仍能说明每一层的输入、动作、奖励和评估边界。
