## 3. 逐簇详述与项目卡片

### C1：STS1/STS2 社区项目现状 —— 最重要发现在本簇

**核心发现：STORM 报告漏掉了 `zhiyue/sts2-rl-agent`——一个与 spec-v2 几乎同构、已跑通的项目**（卡片 [1][2]）。

**项目卡片：zhiyue/sts2-rl-agent**

- **定位**：STS2 战斗 RL 智能体，headless Python 模拟器（对拍反编译 C# 源码验证）+ Gymnasium + MaskablePPO + C# 桥接 mod（仅用于真机验证）。
- **对 C1 决策的价值**：直接回答了 spec-v2 M0 的核心疑问——"headless + 多开采样"不一定要靠带窗口的 mod 通道（STS2MCP 路线），**第二条路是"反编译 sts2.dll → Python 重实现 → 对拍验证"**，实测 ~1,200 战斗/秒、28,000 步/秒，训练后 Act 1 Ironclad 胜率 ~92%。
- **局限**：只有战斗层（无 map/event/shop 决策）；训练目标未到 A5+；52 stars 的小型项目，未受同行评审检验；其 ~92% 胜率未注明置信区间。
- **裁决：采用（作为架构参照与对拍参照，不是直接 fork）**。理由：spec-v2 的 M0 假设是"mod 接口给出合法动作列表 + 状态深拷贝"，这个项目证明了模拟器路线在 STS2 上可行且快；但它是战斗子集，spec-v2 的整局环境（地图/事件/商店）仍需自研，两者不冲突。

**项目卡片：Torch1230/CombatSolver（战斗路线求解器）**

- **定位**：C# Beam Search 跨回合战斗求解器，**本质是 spec-v2 轨道 A（mod 内 C# Expectimax）的社区活先例**（卡片 [3][4]）。
- **价值一（架构）**：其"根状态捕获 → 后台模拟分支 → 预测/执行分离 → 状态偏离即重搜"的设计与 spec-v2 M0-#4"状态深拷贝"需求完全对应，且已在游戏 v0.111.0 上量产可用。
- **价值二（预警）**：其公开短板正是 spec-v2 需要预判的——长线 BOSS 战误判、**能力牌/长线收益被手写评估函数系统性低估**（作者承认权重没写好）、储君印牌流搜索空间爆炸。
- **裁决：采用（作为轨道 A 的架构参照与已知短板清单）**。

**其余生态**：CharTyr STS2 Agent（HTTP API + MCP，补充 STORM 报告版本信息 [6]）；GitHub topic 扫描无第二个 RL 项目 [5]——**我们没有竞争者，但也没有现成轮子可整体搬运**。

**C1 总裁决**：spec-v2 的 M0 应当把"反编译源码 → 自研模拟器"列为与"mod 接口"平级的环境路线（甚至优先，见 §4 待改清单）。

### C2：AlphaStar / OpenAI Five 训练管线

spec-v2 的 M1（BC）→ M2（PPO + KL 退火）管线在 AlphaStar/SCC 中有直接原型，以下组件可抄：

| 组件 | 先例做法 | 对 spec-v2 的落点 |
|---|---|---|
| **BC 初始化价值** | 97.1 万 replay 的监督策略超 84% 活跃玩家，是 RL 起点与探索多样性来源 [7][10] | 佐证 M1 必要性：BC 不是锦上添花 |
| **KL 锚定（human loss）** | RL 阶段损失 = L_PPO + L_entropy + **L_KL（相对最终监督策略）**[8]；偏离人类策略的动作概率即受罚 [10] | spec-v2 的 KL 锚定对象应明确为"冻结的 BC 策略"，退火期间探测"无 KL 后性能是否塌缩"的实验设计与之相容 |
| **z-statistic 稠密辅助奖励** | 采样人类 build-order 统计量 z，每步奖励 = 当前执行统计量与 z 的距离；独立 value 函数 + GAE [8] | M2 可借鉴为"战斗风格统计量"辅助奖励（如每回合出牌数/保血量分布），缓解稀疏性，且不与终局奖励冲突 |
| **Value warm-up** | RL 初期 value 头噪声大，前 50 步冻结策略只训 value [9] | M2 PPO 启动时的具体技巧，直接采纳 |
| **PBT 超参自动调优** | 学习率/熵成本/unroll 用 PBT 自动演化 [10] | M4 爬坡阶段可选 |
| **league/exploiter** | 12 agent 联赛，PFSP 选对手 [7][8]；轻量化改进有 NeurIPS 2023 先例 [12] | **不采用**（首版）：单人游戏无对手协变问题，self-play 对手 = 环境本身；exploiter 防塌缩的职能由 OpenAI Five 的 80/20 历史对手池替代（更便宜） |
| **AlphaStar 算力量级** | 16,000 并发对局、5 万 steps/秒、200 游戏年/agent [8] | 仅作上限参照，提醒我们与顶级投入的差距；SCC 的 1,000 环境/30 游戏年是"可及"参照 |

**C2 裁决：采用**（human loss、辅助统计量奖励、value warm-up、80/20 历史对手池四件套；league/PFSP 首版不采用）。

### C3：长局稀疏终局奖励的信用分配

- **正面先例**：DouZero 证明 **Deep MC 在 long-horizon sparse-reward 卡牌游戏上的收敛性优于 TD 系**（MC 收敛不受 episode 长度影响、无过估计偏差，高方差用大规模并行抹平，γ=1）[13][14]。**这直接支持 spec-v2 已裁定的"整局 Deep Monte-Carlo 主线"**——原来这条主线在文献里站的不是"备胎"位，而是斗地主上打赢过 TD 系的主力位。
- **负面先例**：STS1 上 model-free RL 的失败复盘——一幕 Exordium 已是"episode 太长、奖励太稀疏"，且无 replay 系统拿不到专家数据 [15]；CombatSolver 手写评估函数对长线收益系统性低估 [16]。
- **正面技巧**：OpenAI Five 防策略塌缩：**80% 对局打当前自我、20% 打历史版本** [11]——比 league 便宜得多的防塌缩机制，采纳进 M2/M3。

**C3 裁决：采用**（DouZero 论证迁移为 M3 整局 MC 的文献依据 + OpenAI Five 80/20 对手池；需要防备的是 shaping 风险，spec-v2 已有 potential-based 塑形的备选，维持）。

### C4：回合制卡牌 RL 的可行规模与算力

- 规模参照值：同构项目在**单机 CPU** 上 ~1,200 战斗/秒、28,000 步/秒，已支撑数百万 episode 的 MaskablePPO 训练（Act 1 92%）[18]；Two-Step RL 显示"构建期/战斗期分阶段训练"有效（万局随机对局 78.5% 胜率）[17]。
- 对照上限：AlphaStar 级投入是 16,000 并发对局/5 万 steps/秒 [8]——我们不可能也没必要对标。

**C4 裁决：需 M0 实测**。参照值已取得：若 M0 spike 的自研模拟器吞吐 ≥ zhiyue 基准的同数量级（数百至千级战斗/秒），则 M2 轨道 B 的采样预算可定；若显著低于此，先怀疑模拟器实现质量而非算法选型。

### C5：类肉鸽/长序列游戏 RL 先例

- NetHack Learning Environment：肉鸽 + 快仿真兼备的环境，单核 14.4k 步/秒，但 **NetHack Challenge 中符号/深度 RL/混合方法全部未能通关**[19]。
- ICRL 2026 复盘：失败根因之一是**环境接口缺陷**（大部分游戏内容不可交互/难交互）；修正观测与动作参数化后 from-scratch RL 有实质改进 [20]。

**C5 裁决：采用原则**——"环境接口质量是一级设计因素"。对 spec-v2 的含义：M0 六项门槛是对的，且观测完备性审计（哪些实体/效果必须入观测）应与吞吐 spike 同等重要；STS2 与 NetHack 的关键差异在于 STS2 信息近乎全可见 + 战斗子问题可分解（M2/M3 分层），这正是我们相对 NetHack 悲剧的机会所在。

### C6：LLM 智能体路线边界

- AgenticSTS 细节核实（与 STORM 报告结论一致并细化）：技能库把 A0 胜率 3/10 → 6/10，**但 Fisher p≈0.37，作者自认不显著**；爬塔模式 A6-A8 需要赛后记忆更新；对比 STS2MCP/CharTyr 0/5 全败 [21]。
- 结合 C1 生态扫描 [5]：LLM harness 多为个人玩具项目（0-1 star）。

**C6 裁决：不采用为主对照；保留为 M4 弱基线**。理由：LLM 路线的天花板证据（A6-A8 需外部记忆库辅助、统计不显著）低于我们 A10 目标；但 AgenticSTS 开源的 298 局轨迹可作 M1 BC 数据的**质量参差参照集**。注意勿在文档中引用"技能库胜率翻倍"时不带显著性警示。

## 4. spec-v2 待改清单（仅建议，不动基线）

调研后认为 spec-v2 值得修订的点，按影响排序：

1. **【高】M0 增加环境路线 B：自研 headless 模拟器**。当前 M0 假设环境 = mod 接口（STS2MCP 式）。`zhiyue/sts2-rl-agent` 证明了第二条路（反编译 sts2.dll → Python 重实现 + 对拍 + 桥接 mod 验证）在 STS2 上可行且吞吐高一个量级。建议 M0-#1 的 spike 同时验证两条路线的吞吐与工程成本，再定主环境。需同步评估：反编译源码的许可证问题（sts2.dll 逆向用于研究的合规性，需用户裁定风险偏好）。
2. **【高】M2 训练细节补四件套**：KL 锚定对象明确为冻结 BC 策略；战斗风格统计量辅助奖励（z-statistic 模式）；value head warm-up（前 N 步冻结策略）；80/20 当前自我/历史自我对局配比防塌缩。全部有先例出处（[8][9][11]），可写入 spec 的训练章节。
3. **【中】M3 主线的文献依据升级**：整局 Deep MC 主线原先主要靠内部论证，现可引 DouZero（MC 收敛不受 episode 长度影响、γ=1、并行抹方差）作为直接文献支撑 [13]，加强该章节说服力。
4. **【中】轨道 A 引入 CombatSolver 为先例参照**：其根状态捕获/分支模拟/预测执行分离的架构与已知短板清单（长线收益低估、特定流派搜索爆炸）应写进轨道 A 的风险节，作为 Expectimax 评估函数设计的反面教材。
5. **【低】M4 弱基线增加 AgenticSTS**：作为 LLM 对照组，引用其数据时须带 p≈0.37 的显著性警示。
6. **【低】M0 观测完备性审计升格**：由 NLE 复盘教训 [20]，建议把"哪些实体/效果必须入观测"的审计列为与吞吐 spike 平级的 M0 交付物。
