# 第一、二幕全卡统一入口与 main 整合

日期：2026-09-14。授权见决策 E12；基线为 main `615cffa`，实施工作区为 `sts2-act12-main` / `codex/act12-full-card-main`。本报告区分源码准入、真实行为验证、运行构建和训练边界。

## 问题与修复

交接中“怪物已经合入”只说明源码合并。现场核查发现，全卡 `IroncladEnv` 仍只有第一幕 5 个遭遇，而 main 本地 ignored 后端是 2026-09-12 的旧构建，未包含集成入口。单独的 35 牌 `EnemyPotionBattleEnv` 支持第一幕，并不能证明全卡入口也可使用这些敌人。

本轮修复以下实际缺口：

1. 全卡契约补齐第一幕 20 个普通、精英和 Boss 遭遇，另接入蘑菇与苏醒乐加维林两个事件战斗变体。第一、二幕的遭遇与幕对应由同一契约生成到 C++，防止诊断脚本和后端各自猜测分幕。
2. 集成 C++ 原来只将第二幕三个 Boss 标为 Boss 房间；现复用锁定后端的 `isBossEncounter`，覆盖第一幕三个 Boss。
3. 六火亡魂的 Inferno 已生成 Burn+，但全卡注册表仍将 Burn 的最大升级次数写为 0，导致战斗在规范化观测时抛错。现允许这个已有状态牌版本；没有增加模型字段或维度。
4. 修复干净构建路径的补丁、生成头文件顺序，并在构建末尾核对敌人契约、全卡契约及注册表三项指纹。
5. 固定涉及运行指纹和冻结校验的文本换行。新工作区曾将冻结比较代码及统一实体契约转换为不同换行，造成相同内容的 SHA 不匹配；恢复原已绑定字节格式，未改写冻结文件的预期 SHA。

main 实际运行的最终复验为 **1,345 项 CPU 回归通过**（61.32 秒，0 失败、0 跳过），另行执行的 **C++ 夹具 1 项通过**（2.13 秒）。本机后端 SHA-256 为 `2c3256c28c5e3701e2705ec297f07017ce2f36a5230b7da682cdf78f061ea28c`；原五遭遇采集器的后端指纹已绑定到这个实际构建，范围未扩大。日志为 `reference/act12-main-build.log`、`reference/act12-main-cpu-regression.log`、`reference/act12-main-cpp-status.log`，运行定位与保留检查为 `reference/act12-main-runtime.json`。

旧后端完整保存在 `third_party/sts-lightspeed-before-act12-20260914`，原 1,414 个非 Git 元数据文件的 SHA 全部一致。原交接说明仍为未提交文件、内容未修改；A 路径工作区的所有已跟踪文件和后端二进制哈希与本轮开始时一致。诊断原始记录和相关日志已复制到 main 的 ignored reference 目录。

## 使用与边界

在 main 根目录运行 `scripts/build-enemy-potion.ps1 -Python python -Jobs 1` 构建，使用 `sts.env.ironclad.IroncladEnv`，按契约提供 A20 场景并显式 `diagnostic=True`。全卡注册表、遭遇白名单与幕映射都位于 `sts/env/ironclad-expansion-contract.json` 及 `ironclad-registry.json`。

事件只接入战斗部分，不处理事件选择、支付、奖励领取或两场衔接。诊断使用人工卡组和随机合法策略，允许明确的外部动作预算截断；初始化成功不等于该牌一定被打出，更不等于所有组合行为正确。逐卡实际出牌情况单独统计。

`training_admitted=false`；本次没有扩大原五遭遇采集器、训练池、正式 Gate 或完整 RunEnv。A 路径分支和训练运行保持原状，冻结 public/MLP/Set 历史入口仍各自保留。`battle_reward_v1`、gamma 1、beta 0 和不可变 eval seeds 不变；旧 checkpoint 应继续使用各自源码、依赖和运行指纹。
