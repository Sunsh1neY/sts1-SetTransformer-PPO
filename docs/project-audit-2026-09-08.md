## 3. 下一步的架构改进

### 3.1 扩容前统一检查观测容量与动作容量

这是最明确的潜在阻断：当前敌人观测有五行，动作编码却只允许三个目标列。
`slot * 3 + target` 无法表达攻击敌人 3、4；例如把 `slot=0,target=3` 编成 3，实际会变成
“手牌槽位 1，目标 0”。它不是多补一列敌人特征就能解决的。

锁定后端的 `src/combat/MonsterGroup.cpp` 中，Gremlin Gang 分支创建四个敌人，
Lots of Slimes 分支创建五个。已在 Week 5–6 计划中标明暂不开放这些候选。
还要核对每个候选遭遇在分裂、召唤后是否超过目标索引 2。当前三遭遇没有这个缺陷。

中等档配置真正实现时，用一个小型输入/动作契约集中记录手牌容量、目标容量、牌堆容量、
字段顺序、类别表和版本；不要散落修改 `31`、`3`、`5`、`20`。如保留五目标，动作数会变为
`10*5+1=51`，须先登记决策并联动 C++、mask、模型头、checkpoint 与轨迹；本审核未改协议。

### 3.2 保持数值编码在模型侧，并让 MLP / Set 共用约定

初始 S1 将原始 HP 等数值直接送进 Linear→Tanh。本次固定 `torch.manual_seed(20260908)`，
取三个遭遇各一个真实初态（seed `100000+i`），全局投影中 `abs(output)>0.99` 的比例为
91.67%。这只是初始化探针，不能据此断言 PPO 失败。

同期 S2 已增加明确的正数缩放和 checkpoint 编码版本。用同一初始化及同一批观测复查，
全局投影上述比例降为 0%。该改进已经落地；后续 Set 编码器应共享缩放定义，避免两条路径
各维护一套常量。当前 wrapper 继续输出原始事实；不要借此加入可训练 wrapper 或评估集统计。

### 3.3 S3 先明确 rollout 数据边界，再写 PPO 更新

现有 `run_episode` 适合回合执行验收，但只返回动作序列、步数与总回报，缺少 PPO 所需数据。
建议 S3 使用一个显式的批量记录结构：本步观测及 mask、动作、旧 log-prob、旧 value、奖励、
任务终止标记和批次末状态。环境不碰模型，模型不访问 C++ 内部对象。

更新时从原观测的原 mask 复算分布；不要将下一步 mask 错配给旧动作。
任务硬超时仍是终止且不自举，采样批次截断则按 D20 区分处理。概率只在需要交给执行接口
时转成 NumPy；用于训练的 log-prob、熵和 ratio 留在 torch 路径。无需为此改成通用 RL 框架。

### 3.4 把可复现性做成每次训练的交付项

同期 S2 已有源码 ZIP、配置、数据哈希、环境/模型种子、扩展哈希、曲线与 checkpoint，是可复用的起点。
S3 再补优化器、训练计数和 RNG 状态的恢复语义；记录训练/开发诊断区间及正式评估文件哈希。
不要只保存 commit hash：本工作树含未提交与未跟踪代码，单凭提交号不能还原本次运行。

当前两个任务曾同时修改同一工作区并运行计算，性能数字出现明显波动。后续并行实现适合使用
独立工作树，性能验收单独运行；这能减少文件互相覆盖和测量干扰。本次未替用户移动任务。
