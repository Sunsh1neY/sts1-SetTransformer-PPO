# STS 奖励策略：v5 → v6 修改任务书

日期：2026-09-08
对象：负责项目规格与训练实现的开发 Agent
性质：依据用户本次裁定编写的升级指令，可直接交给 Agent 执行。

> 当前未取得 v5 原文及真实仓库，因此本文不是已经合并完成的全量 spec-v6，也不声称代码已修改或测试已通过。请以仓库中的真实 v5 为底稿，将本文要求合入 v6；保留无关章节、已有架构决策和历史验证记录。本文中的字段名为建议契约，映射到实际代码时保持语义一致。

## 1. 本次必须落实的裁定

我要把奖励策略明确分为两个正式任务。最终完整爬塔以提高整局通关率为目标；当前独立战斗实验以打赢并保血为目标。不同模型在同一任务内共用奖励，不要求不同任务使用同一个公式。

| 项目 | 完整爬塔任务 `run` | 独立战斗任务 `battle` |
|---|---|---|
| 正式目标 | 最大化最终通关概率 | 最大化战斗综合成绩 |
| 成功奖励 | 首次最终通关时 1 | 首次战斗胜利时 `1 + 0.5 × h_exit` |
| 其他步骤 | 0 | 0 |
| 失败、任务硬超时 | 0 | 0 |
| 折扣 `gamma` | 1.0 | 1.0 |
| 当前塑形系数 `beta` | 0.0 | 0.0 |
| Episode 边界 | 整局真正结束 | 该场战斗真正结束 |
| 成绩解释 | 平均回报等于通关率 | 综合成绩，不等于完整爬塔胜率 |

不要因为当前环境只实现了战斗，就把每场战斗胜利标记成完整通关。也不要为了本次奖励修订扩写整个地图、事件或构筑系统：当前可实现部分立即落实；尚不存在的完整流程写成明确接口契约并标注未接入。

文档版本 `v6` 与运行时奖励版本是两个概念。建议分别使用 `battle_reward_v1`、`run_reward_v1`；如果仓库已占用这些名称或旧实现语义不同，采用新版本名，不能覆盖已有含义。

## 2. 完整爬塔的正式奖励

动作索引为 `t = 0, ..., T-1`，`r_t` 是执行动作 `a_t` 后返回的奖励：

```text
r_base[t] = 1  当且仅当本次转移首次完成约定的最终通关目标
r_base[t] = 0  其他所有情况
gamma = 1.0
beta = 0.0
r_train[t] = r_base[t]
```

不累计单场战斗的基础分或 HP 分；不为伤害、格挡、杀敌、出牌、拿牌、遗物、金币、每幕完成或特定构筑发额外奖励；不加入每步惩罚。最终剩 1 HP 和满血通关都得 1。

对完整轨迹，`G = sum(r_base) = 1{通关}`。在固定开局分布和规则下，`E[G] = P(通关)`。这一解释要求任务有明确的结束机制；规则上限应公开并版本化，不能依赖训练程序偶然中断来定义失败。

在启用 `run` 正式训练前，必须从真实项目规则中落实：角色、难度、开局分布、最终 Boss/终点定义、是否包括额外终点、任务上限及失败条件。将其保存为 `task_spec_id` 或等价配置指纹。本文没有替用户决定“第三幕结束”或“击败心脏”等未提供的具体目标；缺少成功谓词时拒绝启动正式 run 训练，不能静默猜测。

### 2.1 全局回报不能在战斗结束处断开

普通战斗胜利 → 战后奖励选择 → 地图或下一阶段，是同一个 run episode 内的转移。

- 内层 BattleEnv 可以返回局部 `battle_done`。
- 外层 RunEnv 不得直接将其映射为全局 `terminated`。
- 战后回血、选牌、路线与后续生存的价值，由最终通关结果评价。
- 全局累计器、PPO episode 标识、DT 轨迹标识和目标 RTG 不在普通战斗结束时重置。
- DT 可使用有限上下文窗口；窗口滑动不代表任务终止。

建议日志区分 `battle_won`、`run_won`、`task_outcome`、`termination_reason`，避免一个 `win` 字段同时表示两种成功。

## 3. 当前独立战斗的正式奖励

```text
h_exit = hp_exit / max_hp_exit
r[t] = 1 + alpha_hp * h_exit  本步首次结算战斗胜利
r[t] = 0                    其他情况
alpha_hp = 0.5
gamma = 1.0
beta = 0.0
```

`hp_exit` 与 `max_hp_exit` 在最后动作及连锁效果、战斗结束效果全部结算后，同一时刻读取。若已实现战后自动回血，则包含该效果；不包含后续选牌、地图事件或营火效果。不能为满足该评分而新增当前范围外的游戏机制。

要求 `max_hp_exit > 0` 且 `0 <= hp_exit <= max_hp_exit`。非法数值应显式报错并排查结算问题，不用静默裁剪掩盖问题。胜负由游戏规则结算器决定；同时死亡等边界不能由奖励函数重新裁定。

奖励最多发放一次。终局后的 `step()` 按现有接口规范拒绝调用或返回无新增奖励的终局结果，不能重复领取成功奖励。

该目标为 `J = p × (1 + 0.5q)`，其中 `p` 为战斗胜率，`q` 为获胜条件下平均退出血量比例。因此它允许一定胜率与保血之间的交换，不是严格字典序“胜率永远优先”，也没有证明等价于全局最佳策略。`0.5` 是固定实验权衡，不宣称最优。

若 v5 写有“后续默认调一次 HP 系数”，v6 改成：本次正式对照固定 0.5；任何后续改动另建奖励版本并处理数据兼容性。

## 4. 真终止、截断与异常

| 场景 | 奖励/状态 | 后续价值处理 |
|---|---|---|
| 当前任务成功 | 发一次对应成功奖励，真正终止 | 不自举 |
| 死亡或规则规定的失败 | 0，真正终止 | 不自举 |
| 任务硬上限导致失败 | 0，真正终止，记录原因 | 不自举 |
| PPO rollout 收满但任务未结束 | 当前实际奖励，任务继续 | 使用边界后继状态价值 |
| 外部时间限制后 reset | 外部截断，不能假装失败 | 使用 reset 前最终观测自举；不跨 reset 递推 GAE |
| 程序崩溃、非法状态、数据损坏 | 标记异常轨迹 | 不伪造零回报失败样本；单独报告 |

若规则上限是任务的一部分，把剩余步数或回合预算放入允许的观测中，并统一计数单位。最后允许的一步是否仍可获胜，遵循已有明确规则；若未定义，建议先结算该步真实胜负，再对仍未结束的任务判超时，并写入任务版本与测试。

对于 Gymnasium 风格接口，任务内硬失败使用 `terminated=true, truncated=false`；外部截断使用 `terminated=false, truncated=true`。实际后端若用其他标志，适配层必须保留这一区别。

## 5. PPO、Set-PPO 与 DT 的统一口径

完整轨迹的真实回报统一为：

```text
G[T] = 0
G[t] = r[t] + G[t+1]      # gamma = 1
```

不除以动作数或回合数，不暗用 PPO 默认 `gamma=0.99`，不对某个模型单独追加奖励或裁剪。优势标准化属于训练处理，不修改存盘的奖励与真实 RTG。

### 5.1 PPO 的边界与价值目标

允许继续使用 GAE，`lambda_gae` 与 `alpha_hp` 是独立参数；本次不凭奖励修订更改现有 GAE 超参数。

```text
delta[t] = r[t] + gamma * bootstrap_mask[t] * V_old(next_obs[t]) - V_old(obs[t])
A[t] = delta[t] + gamma * lambda_gae * trace_mask[t] * A[t+1]
value_target[t] = stop_gradient(A[t] + V_old(obs[t]))
```

`bootstrap_mask` 在真正终止时为 0，在非终止截断时为 1。`trace_mask` 只在下一条样本确属同一条连续任务轨迹且可参与本次递推时为 1；终止、reset 边界和本次 buffer 尾部为 0。buffer 尾部仍可通过 delta 自举。

自动 reset 的向量环境必须取 reset 前的最终观测作为截断转移的 `next_obs`，不能用新 episode 的初始状态。GAE/value target 是训练估计，不应被存为 DT 的完整真实 RTG。

完整爬塔的理想价值是“从当前状态按当前策略继续通关的概率”；若可见观测不足以决定完整状态，则理解为给定可见信息的条件期望。神经网络的数值预测不保证始终落在 `[0,1]`，本次不因此强行增加 sigmoid 或改变 value loss。

### 5.2 DT 数据

- 在原始完整 episode 上先计算 RTG，再切训练窗口，不能以窗口尾部为终局。
- 完整 run 成功轨迹中，每一步真实 RTG 都为 1；失败轨迹都为 0。这是预期现象。
- 战斗终局分数为 1.3 的完整轨迹，每一步真实 RTG 都为 1.3。
- 中间战斗边界不切断 run 的奖励链；上下文窗口无需覆盖整局，但 RTG 必须覆盖后续整局。
- 对外部截断且未恢复至终局的轨迹，不赋予“失败 0”的精确 RTG。基础 DT 数据流程排除此类轨迹；如未来使用估计标签，必须另立数据方案。
- 推理目标按 `G_target[t+1] = G_target[t] - r[t]` 更新，只使用已经发生的奖励；目标选择只使用训练/开发集。

共享奖励保证任务定义一致，不保证 DT 和 PPO 在随机环境中有相同性能，也不保证 DT 的高回报条件能区分好决策与好运气。评估以实际闭环结果为准。

## 6. 势能塑形：v6 默认关闭，保留研究规范

当前固定 `beta=0`，不要求实现或训练一个势能模型。不得自动拼接“HP＋遗物数＋牌组分”作为替代目标，也不直接把不断更新的 PPO critic 当冻结势能使用。

未来确有数据支持时，可以单独登记实验：

```text
r_train[t] = r_base[t] + beta * (Phi(s[t+1]) - Phi(s[t]))
gamma = 1
Phi(所有真正终局) = 0
```

完整轨迹满足 `sum(r_train) = sum(r_base) - beta * Phi(s[0])`。因此应明确修改任何旧版“塑形累计回报必须逐条等于原分数”的文字：势能塑形保持的是固定起点下的策略排序，并非一般情况下的数值完全相等。v6 基线由于 beta=0，仍严格相等。

研究条件：固定且有界的势能、冻结模型与预处理、固定 beta、固定外生开局分布；所有真终局势能为 0，采样截断不清零；不裁剪塑形奖励或删去负项；仅使用玩家允许获得的信息。按完整轨迹验证抵消恒等式，三类模型同步奖励及 RTG 口径，原始通关结果另存用于评估。

是否启用以独立开发种子的真实通关率、达到指定表现所需交互量及运行成本决定，最终测试集不参与调 beta。目标排序不变不代表一定学习更快。此研究不属于本轮必须开发的功能。

## 7. 数据、配置与版本迁移

至少记录以下语义字段，可复用已有 manifest：

```text
document_version, task_type, task_spec_id, reward_version,
gamma, alpha_hp(仅 battle), beta, potential_version(无则 null),
environment_version, termination_rule_version,
episode_id, task_outcome, termination_reason
```

逐步数据保留 `reward`、终止/截断标志、必要结算信息；如为未来塑形预留 `reward_base` 与 `reward_train`，当前两者必须相等，模型仅消费指定的一套标量训练奖励。

迁移时：

1. 审计旧数据的真实任务、退出 HP 读取时点和终止语义，不能只按文件名判断版本。
2. 奖励语义变化后从可验证的原始字段重算逐步奖励与整条 RTG，产生新数据版本，保留旧版本。
3. 原始字段不足或缺失后续结果时报告无法重算，重新生成；禁止猜标签。
4. 独立战斗数据缺少后续整局结果，不能把 battle win 直接改成 run win。最多作为明确标注的战斗预训练数据。
5. 若战斗公式及结算时点完全未变，仅文档升版不必假造数值变化；验证一致性后记录其与 v6 契约的兼容关系。
6. 旧 checkpoint 不自动成为新目标下已训练模型；可作为显式 warm start，记录来源并在新任务上重新评估。恢复训练必须核对任务/奖励元数据，不能静默混用。

## 8. Agent 执行顺序

1. **定位真实 v5。** 读取仓库指令、当前规格、决策日志、奖励结算、wrapper、PPO、数据生成及评估入口。列出真实文件映射和冲突项，不编造章节号。
2. **合并 spec-v6。** 按仓库版本约定保存 v6，更新“当前规格”入口；保留 v5 历史。修改奖励目标、终止、配置、离线数据、评估和未决事项中的交叉引用。
3. **同步决策日志。** 用下一个可用编号记录本次裁定；旧决策保留历史并标明被哪些条款替代。不能把历史测试计数当作 v6 测试结果。
4. **落实当前可执行路径。** 单一权威奖励计算点；训练端不重复加分。核对 HP 时点、只发一次、gamma、硬超时和 rollout 自举。完整环境已存在则接入 run 规则；未存在则只添加必要契约/配置校验，不伪造完整环境已完成。
5. **处理数据兼容性。** 提供版本检查与适用的重算入口；没有旧数据则说明“不适用”，无需创建空迁移工程。
6. **执行下述必要验收。** 使用最小确定性案例验证公式与边界，再运行受影响模块的既有回归；可做小规模学习诊断，不以短训练证明奖励最优。
7. **提交交付报告。** 汇报改动文件、v5→v6 差异、已执行测试与结果、数据影响、未接入功能、可复现命令。不要默认发起长时间正式训练或大规模离线数据生成。

## 9. 验收矩阵

| 编号 | 案例 | 必须满足 |
|---|---|---|
| R1 | 战斗非终局、失败、任务硬超时 | 奖励均为 0；后两项不自举 |
| R2 | 战斗胜利，退出 HP=60/80 | 唯一一次奖励为 1.375 |
| R3 | 战斗胜利，结算前 50/80，已实现战后回血到 56/80 | 奖励为 1.35，读取同一结算时点 |
| R4 | 再次调用终局 step、反序列化终局状态 | 不重复发放成功奖励 |
| R5 | run 中普通战斗胜利、选牌、幕切换 | 奖励为 0，全局 episode 不结束 |
| R6 | run 最终通关；死亡；规则超时 | 完整累计回报分别为 1、0、0 |
| R7 | run 通关时 1 HP 与满血 | 均仅得 1 |
| R8 | 同结果但轨迹长度不同 | 无折扣累计相同；训练配置 gamma=1 |
| R9 | 非终局 rollout 边界，r=0、V(next)=0.4、V(now)=0.3 | delta=0.1；真终局失败对应 delta=-0.3 |
| R10 | 自动 reset / 外部截断 | 自举取旧 episode 最终观测，GAE 不跨 reset |
| R11 | 完整轨迹奖励 `[0,0,1.3]` 后截窗口 | 原始 RTG `[1.3,1.3,1.3]`，窗口保留对应值 |
| R12 | battle 旧数据尝试作为 run 成功标签 | 拒绝错误迁移；缺少整局结果不得猜测 |
| R13 | 相同任务轨迹分别经三类模型的数据路径 | 原始逐步 reward、gamma、真实 RTG 一致 |
| R14 | 非法 HP、未配置 run 成功谓词、任务/奖励版本不匹配 | 显式校验失败，不静默回退 |

若完整 RunEnv 尚未实现，R5–R7 只能通过独立奖励函数或最小状态机测试验证契约，并在报告中标为“完整环境集成待完成”；这不能算真实 run 端到端验收通过。未来启用塑形时另补终局势能归零、截断保留势能和累计抵消测试。

## 10. 评估与完成定义

同一任务的模型固定初始状态分布、种子协议、成功条件、上限、奖励版本及评估动作选择方式。沿用项目已确定的隔离种子和统计协议；战斗与整局结果分表，不直接排名。

- battle：平均综合回报、战斗胜率、获胜条件下平均退出 HP 比例、任务超时率。没有胜利时条件 HP 指标为 N/A，不写成 0。
- run：真实通关率、置信区间、失败/超时分布、交互与训练成本。HP 和构筑统计可用于诊断，不转成额外奖励。
- 中断、崩溃等异常数量单独报告；不能靠删除困难案例抬高评估成绩，也不能将基础设施错误当作正常游戏失败。

本轮完成表示：v6 规格与决策同步，当前实际可用环境的奖励/边界正确，三种方法的数据契约一致，数据版本处理明确，受影响测试有真实结果。它不表示完整爬塔环境已经实现，不表示终局稀疏奖励必然容易学习，也不表示 0.5 已被证明最优。
