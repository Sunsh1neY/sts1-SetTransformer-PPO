# STS 遗物静态审计与分批导入计划 v1

日期：2026-09-14  
项目：Sunsh1neY/sts1-SetTransformer-PPO  
交付性质：基于已读取代码和本地合并报告的静态审计、执行计划，以及上游枚举审计底表；不是全遗物行为验收报告。未修改仓库，未启动训练，未在用户机器上重新构建或运行测试。

## 0. 核心裁定

**每个已拥有的遗物实例作为一个 RELIC 实体进入共享 Set Transformer。遗物身份和必要的公开动态状态必须进入模型；不能只让遗物在环境内部生效，也不能只留在 info、日志或场景初始化参数中。**

保留现有合格 Set 主干、PMA、A 路径两阶段 Pointer 和联合 PPO。不因遗物扩展重新选择动作架构，不增加一个“遗物专属 Transformer”，不把被动遗物伪造成可点击动作。

本轮重点是 Ironclad 的第一、二幕独立战斗环境。所有遗物都应进入审计目录，但“完成全目录审计”不等于“立刻实现所有完整爬塔功能”。战斗内效果、入场条件、跨战斗状态和战外效果分开标记。超出当前任务范围的机制应明确保留为范围外，不能假装实现，也不能通过删除真实初态中的遗物让场景混入正式训练。

## 2. 已完成的静态审计

### A01：不是从零开始——当前白名单已有 8 个遗物

`sts/env/full-card-public-contract.json` 明确登记下列 8 项，ID 为 1–8。全卡入口继承该遗物边界；今天的本地报告也记录该边界不变。[S02][S05][L01]

| 项目 ID | 规范名称 | 第一轮必须补齐/核对的验收重点 |
|---|---|---|
| 1 | Burning Blood | 战斗退出回血与最终退出 HP 时点；真终局后不得二次发奖/回血 |
| 2 | Lantern | 入场首次能量增益；中途快照恢复不能重新发放 |
| 3 | Anchor | 开战格挡初始化；首轮消耗后恢复不能重新添加 |
| 4 | Bag of Preparation | 初始抽牌阶段与其他抽牌效果顺序、手牌上限 |
| 5 | Vajra | 初始化力量恰好一次；与来源场景中已有状态不得重复叠加 |
| 6 | Oddly Smooth Stone | 初始化敏捷恰好一次；相同状态重复 reset/restore 的正确边界 |
| 7 | Blood Vial | 入场回血时点、满血截断；锁定上游附近有正确性 TODO，须查当前补丁 |
| 8 | Bronze Scales | 伤害事件与反伤；多段攻击、格挡、敌人死亡后的后续结算 |

上述第三列是**应验收的问题清单**，不是本次已通过的行为测试。不能用“白名单有名字”替代机制对拍。

### A02：旧统一实体模型已经有遗物 token

本次直接读取的 `sts/models/unified.py` 有以下路径：[S03]

```text
obs['relics']
    → unified_fields.encode_fields
    → 遍历遗物定义，仅为已拥有遗物 add(kind=3, ...)
    → 遗物类型投影 + type embedding
    → 与 CARD / ENEMY / POTION / PLAYER 同一组注意力
    → 上下文化实体 + PMA
    → Actor 和 Critic
```

旧实现的遗物原始特征宽度为 `len(PUBLIC_CONTRACT['relics']) + 3`，当前即 11：8 维身份 one-hot，以及存在、计数是否已知、缩放后的计数。模型投影到 64 维。它不是“仅在环境中生效”。

但是，此模型绑定旧 public 协议、旧普通动作路径。**它只证明仓库中存在这条路径，不证明当前本地 A 路径训练已经使用同一实现。** 执行时必须沿真实 collector → encoder → batch → model → loss 调用链追踪一次。

### A03：字段足以表达简单子集，不足以自动覆盖复杂遗物

`unified_fields.py` 对遗物只接受 `name / counter / relic_id`，计数在输入侧区分 None 和 0，但没有通用的消耗状态、每回合已触发状态、多类事件进度、关联卡牌等约定。[S04]

锁定上游 `Player.h` 已有多个独立计数器、`haveUsedNecronomiconThisTurn` 和 `orangePelletsCardTypesPlayed`。这说明新增遗物不一定能塞进单个无类型 counter。[S07]

“补充多少字段”必须由逐遗物审计决定；不要为所有遗物分配一大堆无定义的 `misc_1...misc_32`，也不要把确实影响下一步行为的状态压成模糊的一个数。

### A04：扩白名单有冻结模型与注册表陷阱

- 旧模型 `RELIC_DIM` 随遗物表长度变化。直接把旧表从 8 扩到很多项会改变旧网络输入形状和 checkpoint 解释。[S03]
- `full_card_public.normalize_observation(raw, contract=...)` 的卡牌注册表来自传入 contract，而遗物仍查模块级 `RELIC_BY_NAME`。因此只在新 contract 写遗物，不代表规范化入口自动支持它。[S05]
- `IroncladEnv` 复用该规范化路径，当前仍是继承的 8 遗物边界。[S05]

这是扩展时的具体改造点，不意味着当前 8 遗物输入已经因此出错。建议新扩展使用独立、显式版本化的遗物 registry 和 per-contract resolver，保留历史 public/comparison 入口及其字节指纹，不以改写旧冻结 SHA 掩盖兼容性破坏。

### A05：上游有状态和效果框架，但不等于可直接全面准入

锁定上游有遗物枚举、运行状态字段与开战触发逻辑，应优先复用和修复，不另造一套 Python 遗物规则引擎。[S07][S08][S10]

本次发现两个必须单独排查的风险：

1. `BattleContext::initRelics` 附近明确注释未保持某些效果顺序。应核对本地补丁是否已处理，不能据此直接宣判当前环境错误，更不能直接宣称全部组合与原版一致。
2. 钢笔尖初始化在特定状态下会设置 `penNibCounter = -1` 并配合玩家状态表达效果。**内部 -1 是实现细节，不能无审计地作为“玩家看到的计数”送入 token。** 必须定义规范可见语义并做往返/阈值测试。[S08]

此外，运行中的计数可能存于 Player，而入场值保存在 relic data。应确认每步观测读取的是当前运行值，不是一直重复导出入场旧值。

### A06：上游目录底表已准备，但不是全机制验收

随附 `relic-audit-ledger-draft-v1.json` 转录锁定上游 `RelicId` 的 **181 个枚举项**，包括 `INVALID` 和需辨别的特殊项；去掉 INVALID 为 180 项。该数字是**上游枚举项数，不是原版 Ironclad 可获得遗物数，也不是已实现遗物数**。[S10]

每项分别记录旧白名单成员身份、旧 token 路径状态、推荐批次以及尚未运行的机制/恢复/真实游戏验证。非本次可验证的项目均标为未验证。执行 Agent 应先由实际锁定文件自动复核此转录，再与正版 JAR、当前补丁、实际角色和模式范围比对，补齐漏项和排除理由。

## 3. 遗物审计的合格定义

每个遗物独立记录下列状态，不允许用一个 `supported=true` 混在一起：

| 维度 | 必须回答的问题 |
|---|---|
| 身份 | 原版名称、原版 ID、项目稳定 ID、上游枚举是否有别名或冲突？ |
| 任务范围 | 在 Ironclad 当前战斗任务中可出现吗？仅战外、仅入场、战中、战后，还是跨阶段混合？ |
| 规则 | 触发条件、结算时点、次数、数值、失效条件、与已有卡/敌人/药水的依赖是什么？ |
| 上游实现 | 是只有枚举、已有未核实代码、已被补丁修复，还是确实缺失？ |
| 初态 | 需要计数、已消耗状态、绑定卡、上一房间、首次入场标记等哪些字段？ |
| 公开信息 | 玩家直接可见、可由公开历史重建、不可见内部状态分别是什么？ |
| 观测与 token | 每个有影响的公开字段是否进入正确实体/关系？未知、无效和真实零有没有区别？ |
| 恢复与退出 | snapshot 恢复是否精确？跨战斗数据是否正确导出？获得效果是否重复执行？ |
| 行为证据 | 对拍来源、夹具、真实触发次数和边界覆盖有哪些？ |
| 训练准入 | 哪个入口/哪些初态/哪些组合得到允许？版本、资源上限和限制是什么？ |

**战斗准入建议条件**：身份可解析，所需模拟器状态足够初始化，当前任务内所有会执行的效果已支持，可见字段完整，必要动作/选择/容量接口可表达，并通过该遗物最低测试集。仅有 token 不能弥补环境错误，环境正确也不能弥补模型缺字段。

战外遗物允许在战斗观测中保留身份 token，但只有证明其战斗相关后果已体现在导入初态，且当前战斗不会调用未实现机制时，才可以按“战斗范围支持”准入。不能把这写成完整 RunEnv 支持。

## 4. 正式遗物 token 协议

### 4.1 一个已拥有实例一个 token，不是一个名字一个词

```text
[玩家/阶段实体]
[手牌、抽牌堆、弃牌堆、消耗堆、结算/选择/扣牌实体]
[敌人实体]
[药水实体]
[遗物实例 1] ... [遗物实例 R]
            ↓ 同一个 Set 编码器
            H → 来源/目标 Pointer
            H → PMA → Critic
```

不为全部未拥有遗物生成海量空 token。不把所有遗物压成一条“总加成”替代实体身份。按真实规则处理重复持有和叠层：普通唯一遗物重复输入应拒绝；确有叠层显示的特殊项明确规定实例/层数语义，不凭一般经验扩成任意重复遗物。

ID-only token 在固定目录中可以学习静态效果；没有必要首版引入自然语言描述编码或语言模型。旧 one-hot 加线性投影在身份表示上与 embedding 查表可表达等价，因此 one-hot 不是错误。本计划建议在**新版本**中使用稳定 ID embedding，主要为避免扩大目录时连带改变原始身份特征宽度。

### 4.2 三层数据分离

| 层 | 保存什么 | 不允许什么 |
|---|---|---|
| 引擎完整状态 | 模拟所需的真实内部状态、队列、RNG、绑定引用 | 不可直接整体喂给模型 |
| 规范公开观测 | 遗物身份、允许公开的动态状态、已核验关系 | 不导出 RNG、隐藏牌序、未来意图、内部哨兵或不可知的绑定信息 |
| 模型张量 | 从规范观测转换的 ID、数值、类别、known/applicable 与 valid mask | 不靠读取环境对象/调试 info 补数据 |

推荐规范字段类别如下；这是待落地设计，不是当前仓库已有 schema：

```text
RELIC
  relic_id                       稳定类别 ID，来自追加式 registry
  semantic_state:
    counter / progress           对该遗物有明确定义的计数/阶段
    used_this_turn               需要时保留
    used_this_combat             需要时保留
    spent / enabled / armed      依据机制拆分，不能把不同含义混成 active
    remaining_uses               需要时保留
    event_type_progress          如多类卡牌触发进度，必要时用小型 bit vector
  relation_refs                  仅路由/关联引用，不直接作为数值 embedding
  每个可选状态: applicable + known + value
```

这些是字段类别，不要求所有遗物重复存储所有字段。共享的玩家公开事件统计可保留在 PLAYER_GLOBAL，由遗物通过注意力读取；但要证明相应信息存在且没有重置/可见性错误。counter 的周期、触发阈值、作用域及缩放由 registry 绑定，避免不同遗物复用无定义的编码。

`applicable=false` 表示该遗物没有此字段；`known=false` 表示存在此概念但观察不到；`known=true,value=0` 才是真实零。张量可在遮罩后把未知数值设为 0，但**不能把缺失的模拟器初态补成 0**。后者会改变游戏过程。

短周期计数必须保留临界点的区别；不采用会把“触发前一步”和“触发后”合并的粗分桶或裁剪。需要离散 embedding、one-hot 还是固定缩放按字段选，不为追求小维度丢掉信息。

### 4.3 投影到已有主干，不重造网络

建议在新版本使用：

```math
x_r = E_type(RELIC) + W_id E_relic(relic_id)
      + f_state(values, known, applicable)
```

输出宽度复用本地已验收主干。当前计划可按 64 维接口实现，但先核对实际 A 路径契约；不要将远端旧原型的层数误认为本地最终版本。小 ID embedding（例如 16 维）是可调整的初始工程参数，不是经过训练验证的最佳值。

遗物 token 参加共享 self-attention 且进入 PMA。来源/目标 Pointer 读取经过这些遗物上下文化的牌/药水/敌人表示。Actor 和 Critic 必须都能使用遗物信息。

大部分遗物是被动规则，不新增第一阶段“使用遗物”候选。因遗物产生的真实选牌阶段应由环境提供合法候选，并复用现有选择接口，不在策略内部伪造额外 transition。

### 4.4 关联与顺序

瓶装类遗物须审计“绑定哪个具体卡牌实例”。优先复用当前已验收的关系表示，或采用一次关联特征融合，不默认增加图神经网络、关系 Transformer 或全套新 attention bias。已有卡牌上的公开标记若已能无歧义表达关系，可复用，不为形式整齐重复制造边。

禁止把绑定对象的数组下标、unique_id 或 token 序号直接作为语义特征。相同名字、不同升级/实例的卡必须能正确路由。

**token 排列不变性不等于游戏触发顺序无关。** 重排张量时保持同一物理状态、同一绑定和同一语义顺序不变。若原版某类触发确实受公开获得/排列顺序影响，必须先验证，再表达相应公开顺序关系；不能借“Set 无序”删除真实因果信息，也不能把任意实现数组位置冒充该关系。[S08]

## 5. 后端实施与初态导入

### 5.1 先找已有事件钩子，再补最小缺口

复用锁定 C++ 后端与现有补丁中的规则。逐遗物登记所依赖的真实事件，不强行统一成一个大而全的新框架。需要审查的时点包括：获得遗物、进入战斗/抽牌前后、回合开始、抽牌/洗牌、支付与打出卡、自动/重复打出、造成或受到伤害、失去 HP、耗尽/弃牌、使用药水、击杀/复活、回合结束、战斗退出。

特别区分：打出一张攻击牌与一次伤害命中；攻击伤害与直接失去 HP；手动打出与自动/重复打出；动作队列已经排入与效果真正完成。以原版证据为准，不能靠事件名称猜是否计数。

同事件多个遗物的组合使用确定的结算规则和轨迹日志。原版证据可用本机合法持有的 JAR 作定点仲裁，产物留在 ignored reference，仅提取规格和测试预期，不复制反编译实现进仓库。[S01]

### 5.2 导入阶段必须显式

| 输入类型 | 正确做法 |
|---|---|
| 开战前场景 | 提供足够的持久状态，执行真实开战钩子一次 |
| 已执行开战效果的观察点 | 不重复获得/回血/加能量/抽牌；只支持能明确恢复该阶段的入口 |
| 战斗中快照 | 恢复运行中的计数、已触发/消耗状态、队列和绑定；公开观测不冒充完整快照 |
| 战外永久变化后的初态 | HP/max HP、卡牌升级/变形、槽位等已落在初态中的变化不得重放 on-obtain |
| 真实日志缺必要状态 | 拒绝正式导入或由可验证的早期轨迹重建；不补零、不删遗物、不用模糊说明掩盖缺失 |
| 人工机制诊断 | 可以显式设定计数/状态，但标为 diagnostic/configured，不冒称真实历史复现 |

跨战斗计数本轮至少应有“导入 → 当前战斗推进 → battle_exit 导出 → 下一战斗初始化”的夹具，即使完整 RunEnv 未实现，也可验证状态承接。此夹具不等于已经接入完整爬塔。

可见性协议与模拟器状态协议独立：内部已知但玩家不可见的值可以用于模拟，不因此获得进入策略输入的许可；原本公开但来源日志缺失的值，不可谎称它在游戏中不可见。

### 5.3 三类不能用普通数值 token 糊过去的扩展

- **改变信息权限**：Frozen Eye、Runic Dome。核验原版规则后，分别改造相应可见牌序/意图权限；增加一个身份 token 不会自动解决信息泄露或信息缺失。检查衍生预览、历史字段和缓存是否绕过遮罩。原有“非手牌无序”默认约束只能对已证明的公开信息进行精确例外扩展，不能全量开放隐藏牌序。
- **改变候选或绑定**：Bottled 系列、Gambling Chip、Nilry's Codex。先确认真实可选动作是否能由已有单选/确认/跳过表达；不能假设所有多选都可无损拆成现有单选。确认语义后版本化扩展候选，不静默禁用。
- **改变容量**：Potion Belt。当前公开路径为 3 药水槽、66 普通动作。导入会影响槽位的遗物前，核对实际有效容量、动作映射、mask、候选和恢复协议；不能仅增加 token 而仍固定旧槽位。[S02][S03]

这些例子作为专项审计候选，具体游戏行为和边界以本机原版及实际后端对拍确认。

## 6. 分批导入路线

先完成审计目录与 schema，再纵向打通少量代表，最后按机制族扩展；不按“随机挑 20 个名字”推进。

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| R0：基线与全目录审计 | 核对本地环境/A 路径，自动导出 JAR 与上游目录，逐项分类，审查当前 8 遗物与注册表重复定义 | 每个候选有身份/范围/实现/公开状态/依赖/缺口；未知项不伪装 supported |
| R1：正式 token 通路与现有 8 项 | 新遗物 schema/registry、规范化、编码、batch、Actor/Critic、日志和恢复；现有 8 项完整串联 | 每个已拥有实例恰好对应一个 token（8 项逐一验证）；无遗物与 padding 测试、真实触发测试通过 |
| R2：计数代表闭环 | Pen Nib、Nunchaku、Happy Flower、Incense Burner、Ink Bottle、Sundial，逐项而非同时大改 | 导入值、每步更新、临界触发、跨回合/跨战斗、恢复、known/valid 全部验收 |
| R3：直接/条件效果扩充 | 候选：Bag of Marbles、Red Mask、Clockwork Souvenir、Preserved Insect、Slaver's Collar、Black Blood、Meat on the Bone、Orichalcum | 普通/精英/Boss 条件、首次/重复入场、终局回血等通过；只开放已验收子集 |
| R4：事件链与规则改变 | 按依赖分小批：出牌类别计数、击杀/耗尽、能量/保留、随机生成、复活 | 定向联动、事件顺序、队列边界、卡池/公开状态和恢复通过 |
| R5：关联、选择与可见性 | Bottled、Gambling Chip、Nilry's Codex、Frozen Eye、Runic Dome、Potion Belt 等专项 | 对应关系、候选、权限和容量契约各自完成，不接受“只加名字” |
| R6：扩大初态池与受限训练 | 按已批准准入策略重新审核场景；保留原来源组划分及采样原则；短运行验证后再扩大训练 | 场景/遗物状态完整，collector/update/恢复成功，报告训练与数据变化边界 |

R3/R4 内部顺序由 R0 得到的真实初态阻塞频率、机制依赖、状态可恢复性和测试成本决定。当前没有统计新遗物的真实频率，不预设 50/25/25 等配额，不强制重写已裁定的 source-group 均匀开局和全局 shuffle。

**首个可交付里程碑建议是 R0 + R1 + R2，而不是一次放开所有遗物。** 这不是只做纸面设计：退出时必须能展示真实遗物 token、真实计数变化、一次真实 A 路径前向和一次 PPO 更新。

## 7. 必须执行的验收矩阵

### 7.1 可以靠结构与行为测试确认的结论

| 编号 | 测试 | 必须证明的内容 |
|---|---|---|
| T01 | 旧白名单和无遗物回归 | 扩展不会改变冻结环境/旧模型的行为与文件指纹 |
| T02 | 8 项身份与实际 token 追踪 | token 存在于真实 batch，而非仅存在于 observation/info |
| T03 | 状态语义 | absent、unknown、not-applicable、0、临界值、spent 彼此不混淆 |
| T04 | 计数全周期 | 初值、阈值前后、重置、跨回合/战斗、内部哨兵规范化 |
| T05 | 初始化阶段 | pre-battle 与 mid-battle 不重复运行获得/开战效果 |
| T06 | 顺序与组合 | 多遗物、卡/药水/敌人事件链与原版对拍；包括死亡、复活和多段结算 |
| T07 | 置换与关系 | 重排遗物/卡/敌人 token 并同步路由，语义动作概率与 V 不变；真实顺序变化另测 |
| T08 | Actor/Critic 通路 | 对遗物字段进行受控扰动，验证两个头均有依赖/梯度通路；无目标与特殊动作也检查 |
| T09 | padding 与 NaN | 增加无效行不改变输出；无效输入在进入线性投影前清理；padding 输出与 mask 正确 |
| T10 | 可见性 | 改变隐藏 RNG/隐藏牌序不直接改变规范输入；合法公开权限变化被正确反映 |
| T11 | 路由与过期引用 | 绑定实例正确、相同牌名不误绑；过期 snapshot 拒绝；被动遗物不凭空变成合法动作 |
| T12 | 容量 | 超出已声明预算明确拒绝/按既有外部截断语义处理，不能静默裁掉遗物 token 或伪记失败 |
| T13 | collector 和 PPO | 完整遗物信息随 rollout 保存；old/new log-prob 重评估一致，保持完整动作联合 ratio |
| T14 | 精确恢复 | 同一新版本 checkpoint 下恢复环境/优化器/RNG/计数/绑定后，下一步与下一次更新一致 |
| T15 | 入口隔离 | full-card、独立 enemy-potion、旧 public、comparison 的白名单与指纹不误求并集 |
| T16 | battle_exit/reward | 遗物退出效果结算与最终 HP 口径一致；奖励仅按原契约产生一次 |

梯度测试用非退化的受控夹具与已知通路，避免只有一个合法动作导致 Actor 梯度必为零。不能要求“任意未训练模型在任何状态下改任何遗物都必须明显改输出”；那不是有效验收标准。

置换测试比较**同一个语义动作**的概率，需要同步 action/candidate/target/relation 映射，不是盲比数组相同位置。具有真实语义作用的触发顺序保持不变。

每个遗物至少有正例、未触发反例、边界、重复/不重复触发、生命周期恢复，以及与一个高风险已有机制的交互测试。对拍报告记录“效果实际触发了多少次”，不能用“该遗物在场景中出现过”替代行为覆盖。

### 7.2 必须经过训练或性能实验才能确认的结论

模型已能读取遗物，不等于模型学会正确使用遗物。以下问题不能靠 unit test 或 attention heatmap 宣布解决：

- 遗物 token 是否提升学习速度、战斗胜率或退出 HP；
- 哪些状态字段带来净收益，模型是否学会蓄计数/控制触发；
- 是否泛化到未见遗物组合和新卡组；
- 固定宽度是否足够，吞吐和显存是否满足预算。

有需要时对相同环境、初态、奖励、训练预算设置“完整遗物输入”和“移除特定遗物信息”的**重新训练**对照；仅在训练好的模型推理时删除 token 是分布偏移探针，不等同于公平训练消融。优先让正确的完整输入版跑通，消融不是 R1 阻塞。

保留来源 run/source-group 隔离、既有 eval seeds 不变；报告 seen/unseen 遗物组合、主要机制族、胜率、回报、退出 HP、长度、异常/截断与吞吐。开发用诊断数据与正式 Gate 分开，不依据测试表现反复调参再把它称为独立测试。

## 8. 容量与训练工程

每步实体数应统计为实际各区卡牌 + 敌人 + 药水 + 已拥有遗物 + 玩家/上下文实体。保存 N 的分位数和最大值，采样/更新分别测吞吐与显存。

标准稠密 self-attention 的配对规模随 N² 变化。例：其他条件不变时，100→120 token 的配对数比例为 1.44；这是算术示例，不是当前项目实测速率。优先使用已有变长 batch、分桶和明确资源拒绝策略；没有性能证据不要立即改 ISAB 或减掉遗物信息。

当前 source-group 采样和 PPO 全局 shuffle 原则应继续沿用。若新遗物改变了可准入初态池，须更新 pool/split/content fingerprint 并报告可比性，而不是在一次旧实验中悄悄扩大环境分布。

原 MLP/comparison 已冻结：本轮不要求扩它们来陪新 Set 训练。将旧环境 MLP 与新遗物环境 Set 的分数直接比较，不能归因于架构优势。同一新任务未来比较 Set-PPO 与 DT 时，才要求等信息、同逐步标量奖励与回报口径。

## 9. 版本与奖励：本轮不能偷偷改的部分

维持 `battle_reward_v1`、gamma=1、beta=0、已有退出 HP 时点和不可变 eval seeds。不增加“触发遗物奖励”“拿到稀有遗物奖励”或另一个构筑 bonus。完整 RunEnv 和 `run_reward_v1` 仍是另一任务。[S01][S09][L01]

若审计发现已有遗物退出回血的实现不符合冻结定义，应按 bugfix/机制版本单独记录并说明历史结果影响；不能为了省事改变奖励定义去配合错误行为。

为遗物 registry、公开状态 schema、实体 encoding、后端规则/补丁、动作/选择接口和初态池记录独立版本/指纹。旧 checkpoint 继续使用其原快照；新旧 shape 或语义变化时明确拒绝“精确续训”。有意权重迁移可另建实验，但不能混称恢复。

**仅增加观测字段不自动要求重算历史 RTG。** reward/累计口径变化才需要按新版本重算；观测字段缺失则涉及能否补齐和重新编码。环境规则改变后，旧轨迹本身也可能不再属于新任务，不能只重算回报就冒充新环境数据。未来 DT 数据必须完整保存版本化公开遗物状态。

## 10. 实际改动边界与交付物

应先定位本地当前对应模块，再按下表最小改动；不要因文件名不同重造已存在功能。

## 11. 建议执行顺序

先读取本地现状并确认环境主线与 A 路径的真实版本；保持未提交改动与旧实验。完成 R0 后，把当前 8 项和一项计数遗物从 reset 到 PPO update 纵向贯通，随后完成 R2 其余计数代表。每个里程碑报告已完成、实际命令/结果、失败及修复、未完成和是否允许下一阶段。需要新信息权限、动作语义或范围裁决时，只暂停对应部分，不把整项工作退回纸面讨论。

**第一轮验收展示应包含同一真实状态的 obs.relics、RELIC token 行、batch mask、来源/目标概率、V(s)，以及执行一次真实动作后的遗物状态变化。** 这能直接回答“遗物究竟有没有被模型看见”。
