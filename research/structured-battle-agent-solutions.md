# 复杂回合制战斗 Agent 的动作空间、状态分布与训练数据

状态：研究完成
检索日期：2026-09-13
研究对象：具有多实体、目标选择、牌堆选择、状态触发和长时程回报的回合制战斗环境

## 60 秒摘要

这个问题的核心不是“动作数量大”或“缺少一个决策 Agent”，而是三个接口没有被分开：

1. 战斗策略 π_battle：在已经进入战斗的公开状态下，选择出牌、目标、药水和后续选择。
2. 入场分布 ρ_battle：决定训练时会看到哪些合法的战斗入口。
3. 整局策略 π_run 与 RunEnv：决定路线、选卡、商店、篝火和事件，并生成下一场战斗。

现成研究给出的最稳妥组合是：

- 目前动作数量不大时，保留一个平坦的、环境直接产生合法 mask 的离散动作空间。
- 动作真正变成可变长度或带多级条件时，把它表示成候选动作或自回归参数，而不是把所有组合永久乘进一个全局动作头。
- PPO 不要求先拥有一批人类初始状态；它本来就从 reset 分布在线采集轨迹。需要更广状态覆盖时，先做固定的规则式 Run 前缀生成器或公开场景重采样器。
- 将公开 .run 文件用于来源、牌组、楼层和候选入口研究是可行的；将其直接当作逐步战斗轨迹或精确历史回放则不可行。
- AlphaStar 是最吻合“策略游戏 + Nature”的先例，但它不是简单的 decision Agent 给 battle Agent 喂状态。它的关键是结构化动作分解、监督初始化、旧策略数据和联赛训练。
- MiniRTS 是更明确的两级策略先例：高层 instructor 发出计划，低层 executor 执行；但它使用自定义 RTS 和 7.6 万条指令—执行数据，不能直接证明 STS 的两级系统可行。

因此，推荐的第一阶段不是训练 decision Agent，而是：

自然规则产生的战斗入口 → battle Agent 在线 PPO → 固定来源组和 seed 评估。

只有当战斗 Agent 和入场分布都稳定后，才把 RunEnv 和 decision Agent 接入同一个整局目标。

## 1. 问题的正确形式化

### 1.1 动作空间和初始状态分布是两个问题

强化学习任务不仅由状态、动作和奖励定义，也由初始状态分布定义。对本项目来说，应该分别写成：

- 战斗策略：π_battle(a | o)
- 战斗入口：o₀ ~ ρ_battle
- 整局决策：π_run(u | x)
- 整局状态转移：x, u → RunEnv → 下一场景或战斗入口

动作空间解决的是“模型能做什么”。入口分布解决的是“模型会遇到什么”。把 decision Agent 训练出来再用它生成 battle 状态，实际上是在同时学习 π_run 和 π_battle，并让两个未稳定策略互相决定训练数据。这不是单纯的数据扩充，而是增加了一个新的非平稳学习环。

### 1.2 四种容易混淆的数据

| 数据类型 | 能回答的问题 | 能否直接作为 battle PPO 数据 |
|---|---|---|
| .run / run history 摘要 | 这局用了什么牌、走到哪层、拿了什么遗物、结果如何 | 不能；最多作为来源和入口候选 |
| 规则重建的战斗入口 A | 从标准规则和已核实前缀得到什么合法初始战斗 | 可以作为 reset 分布，但必须记录重采样政策 |
| 带逐步观测、动作、奖励和边界的完整轨迹 | 某一策略怎样在每一步行动以及结果是什么 | 可以用于 PPO 以外的 BC/DT 或离线研究 |
| 任意手工拼接的中途状态 | 某个局部机制是否可测试 | 只用于机制诊断，不能冒充自然分布 |

AlphaStar 的 replay 数据属于第二类和第三类之间更完整的形态：可从 replay 获得逐步观察和动作，并且有大量人类对局。STS 的 .run 摘要通常只有楼层级、战斗级或整局级记录，信息粒度不同，不能因为文件数量多就等价于训练轨迹。[S01][S02][S03][S04][S13]

## 2. 五个视角的交叉结论

| 视角 | 核心问题 | 研究结论 |
|---|---|---|
| 环境接口工程师 | 如何让动作永远合法且可复现 | 环境产生合法动作集合，模型只在 mask 后分布上学习；状态、动作和版本必须共同迁移 |
| 在线 RL 研究者 | 是否真的需要外部训练样本 | PPO 交替进行环境采样和 surrogate 更新；先保证 reset 分布，通常不需要人类动作数据。[S09] |
| 离线 RL 数据工程师 | .run 能否直接喂给 DT 或离线 RL | 只有在存在逐步状态、动作、奖励、终止和可对齐 schema 时才可以；否则只能做来源或候选入口 |
| 游戏 AI 架构师 | 战斗是否应该拆成多个 Agent | 规划与反应可以分层，但分层会引入高层时间尺度、接口和信用分配问题；它不是免费的动作压缩 |
| 资源受限实践者 | 3060 能否训练 | 需要控制模型和实验范围，不需要 AlphaStar 规模；环境吞吐、数据覆盖和评测设计比增大模型更先成为瓶颈 |

## 3. 复杂动作空间的现成方案

### 3.1 平坦离散动作加合法 mask

这是最简单、最容易验证的方案。环境预先声明一个动作上界，模型输出固定长度 logits，环境根据当前状态给出合法 mask，softmax 前屏蔽非法项。无效动作不进入策略梯度。

Huang 和 Ontañón 对 invalid action masking 的研究给出了两点直接支持：对策略梯度而言，在 logits 或分布上按当前状态屏蔽非法动作是有理论依据的；当非法动作比例增大时，mask 相比把非法动作交给环境再惩罚，通常更容易学习。[S07]

它的局限也很明确：

- 固定动作上界必须覆盖所有目标和候选，否则会出现目标重编号或静默截断。
- 一个动作编号如果同时表达多个有条件的选择，动作解码和 replay 映射会变复杂。
- 只有“当前动作合法”不等于后续结算正确；mask 不应承担解析未来效果的职责。

对 STS 来说，若实际动作上界约为几十到一百，平坦动作并不值得为了形式上的优雅而立刻替换。真正需要解决的是二次选择、可变候选和动作协议版本。

### 3.2 分解动作或自回归动作头

当动作是动作类型、作用实体、目标、位置、延迟等多个有条件参数的组合时，可以写成：

π(a | s) =
π(type | s)
π(source | type, s)
π(target | type, source, s)
...

完整动作的 log-prob 是各个条件项 log-prob 的和。每一级都需要自己的候选集合和 mask，PPO 旧策略与新策略必须沿着同一条条件路径计算概率。

AlphaStar 的 Nature 论文和官方材料明确采用了这种思路：动作由带类型参数的函数组成，策略按链式法则自回归地产生动作参数；它还用 pointer network 在变长实体列表中选择对象。[S01][S02][S03]

优点：

- 输出规模不随所有组合的乘积直接增长。
- 变长手牌、敌人或对象列表可以自然接入。
- 动作类型和目标类型的条件关系显式存在。

代价：

- 采样、log-prob、熵和 PPO ratio 要对齐所有参数头。
- 某一级选错后，后面的条件分布没有实际意义。
- DT 要决定是预测一个完整动作 token，还是预测多个参数 token。
- 若同一个动作既可能选择手牌又可能选择弃牌堆，条件状态机必须显式版本化。

建议把自回归动作头作为未来的扩展方案，而不是当前 66 位接口的默认替换。

### 3.3 动态候选动作评分

另一种方案不是让模型直接输出所有可能组合，而是让环境列出当前合法候选，每个候选带一个公开描述符，模型对每个候选评分，再在候选集合上 softmax 或取 argmax：

score(s, candidateᵢ) → logitsᵢ

候选描述符可以引用当前手牌实体、敌人实体、药水实体或选择阶段中的牌堆实体。候选的索引只负责回到环境对象，不能把隐藏实例 ID 或隐藏顺序放进模型输入。

这个方案特别适合：

- 奖励选卡、商店、篝火和事件选项；
- 需要从弃牌堆、抽牌堆或手牌中选一张牌；
- 目标数量随场景变化；
- 希望保持 Set 编码的实体对应关系。

它和 Set Transformer 的关系是：集合编码器负责理解全局和实体关系，候选评分头负责把“某张牌作用于某个目标”重新接回具体实体。只做全局池化再输出固定槽位分数会丢掉“这张牌对应哪个动作”的信息。[S01][S02][S03]

缺点是每个决策需要评估多个候选，若候选很多则需要批量化；此外，候选描述符的字段也属于模型输入契约，不能临时把隐藏信息塞进去。

### 3.4 Action Branching

Action Branching Architectures 通过共享状态表示、再为各动作维度设置分支，避免把多维离散动作完全笛卡尔积展开。论文展示了在高维离散化控制任务中减少输出规模的方式。[S08]

但它隐含了一个重要假设：各维度可以在共享表示下被相对独立地处理。STS 中“先选什么牌，再选哪张牌，再选目标”往往有强条件依赖，所以不能把 Action Branching 直接等同于 AlphaStar 式自回归动作。它可以作为模型结构实验，不能替代选择阶段状态机。

### 3.5 层级策略或 Option

层级 RL 可以让高层选择“目标或子任务”，低层持续执行若干步。它适合真正存在时间尺度分离的任务，例如地图规划和战斗控制，但需要定义：

- 高层动作持续多久；
- 什么时候子任务结束；
- 中间失败如何归因；
- 高层观察到的是哪一个 RunEnv 状态；
- 高层奖励如何从战斗结果传回。

因此，decision Agent 不是“把动作空间拆开后顺便生成数据”的轻量模块。它是一个新的策略和奖励问题。

## 4. 动作空间课程和逐步扩展

### 4.1 Growing Action Spaces

Growing Action Spaces 研究在训练初期主动限制动作集合，逐步扩大到完整动作空间，并通过 off-policy 方法转移价值、数据和表示。它的动机正是组合动作空间中随机探索极低效。[S10]

迁移到 STS 时可以采用“任务阶段”而不是修改同一 checkpoint 的含义：

1. 先训练少量卡牌、少量目标和少量遭遇；
2. 再增加状态牌、药水和复杂目标；
3. 每个阶段使用独立 task_spec_id；
4. 最终必须在完整动作协议和完整 mask 上评估。

不能把“限制动作后的高分”写成完整任务性能，也不能让旧 checkpoint 在动作 shape 恰好相同时静默加载到新任务。

### 4.2 Prioritized Level Replay

Prioritized Level Replay 不要求学习一个高层教师来生成所有关卡。它保存环境已经产生的 level 或初始配置，并根据当前策略在该 level 上的学习潜力重新安排采样；论文用 TD error 估计重放价值，并在 Procgen 上研究样本效率和泛化。[S11]

对 STS，更自然的迁移对象不是抽象 level，而是：

- 公开来源组；
- 战斗入口场景；
- 规则前缀的 seed；
- 卡组/遭遇/药水/遗物组合桶。

可以给每个场景维护“最近训练损失、失败类型或价值不确定性”，但仍需保留均匀采样和未见来源评估，避免训练集变成只追逐最难样本的分布。

### 4.3 Reverse Curriculum

Reverse Curriculum 从靠近目标的可重置状态开始，逐步向更远的初始状态扩展。它要求环境可以可靠地从这些状态开始训练，并能判断哪些状态处于策略“有时成功、有时失败”的学习边界。[S12]

在 STS 中，合法的方向不是任意拼接“低血量、满力量、某张牌在手”的中途状态，而是：

- 先从合法战斗入口开始；
- 若后端拥有完整且公开的状态恢复能力，再从完整可验证的战斗检查点开始；
- 否则只使用真实前缀派生的入口场景，不能把手工中途状态当成自然初始分布。

## 5. .run 和公开 replay 的可用边界

### 5.1 AlphaStar 为什么能利用 replay

AlphaStar 论文使用的是可从游戏 replay 中取得逐步观测和动作的数据，并且为动作、状态和版本提供了相对完整的接口。Nature 页面还公开了在线对局 replay、用于模仿学习的人类 replay 来源、伪代码和架构补充材料。[S01][S03][S04]

AlphaStar Unplugged 进一步把 StarCraft II 做成离线 RL benchmark。它明确指出，离线性能依赖数据中是否覆盖足够多的 state-action 对；它使用的是由数百万场人类游戏 replay 派生的、带逐步动作和结果的固定数据集，而不是只有最终牌组或最终分数的摘要。[S05]

这个先例给 STS 的真正启示是“需要完整的可对齐数据接口”，不是“只要下载很多 run 文件就能做离线 RL”。

### 5.2 STS .run 最适合做什么

公开 STS .run 文件通常能够提供牌组变化、楼层、路线、卡牌选择、遗物、药水、HP 数组、战斗摘要和最终结果等信息。一个公开样本可以看到 master_deck、card_choices、path_taken、damage_taken、current_hp_per_floor、potion_use_per_floor 等字段，但它不是逐步战斗 observation-action-reward 记录。[S13][S15][S16]

因此 .run 可以做：

- 公开来源候选的发现；
- 卡组和升级覆盖统计；
- 训练/开发/保留评估的来源组划分；
- 依据已经核实的规则重建战斗入口；
- 研究哪些卡、遭遇、遗物或药水在真实对局中出现过。

它不能无条件做：

- 直接给 battle PPO 提供动作标签；
- 直接给 DT 提供完整的 state-action 序列；[S13]
- 从最终 master_deck 反推每一场战斗的牌堆顺序和内部状态；
- 宣称重建出的战斗是原局精确回放。

RunHistoryPlus 的源码也说明了一个细节：它可以追加 Neow、卡牌变更、遗物和药水的楼层级记录，但药水使用记录按药水 ID 和楼层记录，并不天然保留所有原始槽位、同层时序和隐藏内部状态。[S17][S18]

### 5.3 正确的 .run 使用管线

推荐把管线写成：

公开 .run → 结构解析 → 来源/版本/内容审计 → 规则前缀重建 → 合法战斗入口 A → 独立环境 seed 重采样 → battle PPO

每个入口至少记录：

- source_path、source_sha256、关联 run group；
- source build、角色、进阶、楼层和遭遇；
- 入口时点；
- 原始来源字段和规则推导字段；
- 环境 seed；
- 未观测内部状态的重采样政策；
- action schema、observation schema、容量和 reward version。

如果缺少完整内部状态，就把 exact_historical_replay 设为 false，并明确说明敌人内部随机性、牌堆顺序或跨战斗 RNG 是独立重采样的。

Jialeiv 项目最值得吸收的不是它的胜率，而是失败分析：它发现用知道真实未来抽牌顺序的 MCTS 当老师时，单帧前馈学生很难模仿；它还观察到小网络比较容易学会地图和选卡这类判断型决策，而战斗序列更像规划问题。[S23][S24]

## 7. 你应该采用的组合

### 7.1 当前动作方案

推荐保留：

- 一个版本化的平坦直接动作协议；
- 环境产生完整合法 mask；
- 牌、敌人、药水和选择项作为公开实体；
- 对每个有条件的选择使用候选集合；
- 二次选择进入显式 selection phase，而不是自动代选。

具体来说，直接的“手牌—目标”和“药水—目标”可以继续使用一个固定动作头；当某张牌要求从弃牌堆、抽牌堆或手牌选择对象时，新增的是候选动作列表和选择阶段，不是把所有可能牌 × 目标 × 牌堆 × 选择次数一次性乘进全局动作数。

### 7.2 当前数据方案

推荐三层来源：

1. 自然默认入口：标准牌组和规则环境 reset，用来保持 battle PPO 的基本 on-policy 训练闭环。
2. 公开派生入口：从已审计的真实 run 前缀和完整卡组得到合法战斗入口，再用独立环境 seed 重采样未观测内部状态。
3. 机制诊断入口：只用于测试特定牌、状态或容量边界，不混入自然分布的总体胜率。

先用均匀来源采样建立基线，再按来源组、遭遇、卡组类型和失败模式做受控重采样。只有基线存在后，才考虑 PLR 风格的学习潜力采样。

### 7.3 当前训练方案

对 3060 级别设备，优先使用：

- 小型 MLP 作为结构对照；
- 64 维左右的 Set 表示、少量注意力层和候选评分头；
- CPU 并行运行环境，GPU 负责模型前向和更新；
- 先使用 FP32 验证，AMP 只在数值和恢复边界稳定后作为性能选项；
- 固定短预算、多初始化和固定评估集；
- 训练健康度先看 mask、奖励、终止、自举、价值误差和数据分布，再判断模型容量。

大模型不能替代缺失的状态覆盖，也不能修复错误的动作—mask 对齐。

## 8. 明确不建议的做法

- 现在就同时训练 decision Agent 和 battle Agent，再把结果归因到任一模型。
- 把最终 master_deck 当作每场战斗入口。
- 把公开 .run 的楼层摘要当作逐步动作标签。
- 把不同来源 run 的最终结果拼成一个“专家轨迹”。
- 用看到真实未来牌序的 MCTS 直接给只看当前公开观测的模型打标签。
- 为了让旧动作 head 继续工作而自动截断实体、删除未知牌或压缩目标索引。
- 看到训练胜率上升就宣布对自然对局泛化；必须在未见来源组、固定 seed 和完整动作协议上评估。

## 9. 最终裁决

对你的问题，现成方案不是单一算法，而是一套组合：

动作：当前规模用 flat masked categorical；二次选择用 candidate phase；真正需要时再引入自回归参数头。

状态：用规则产生的自然入口和经过审计的公开 run-derived 入口；用统一或 PLR 风格采样管理覆盖，不训练 decision Agent 来“随机找状态”。

数据：.run 做来源和入口研究；完整逐步轨迹另行采集；PPO 走在线环境交互；DT/离线 RL 只接受完整状态—动作—奖励轨迹。

架构：先稳定 battle Agent，再做 RunEnv 和 decision Agent；AlphaStar 的联赛和规模只作为上限参照，不作为笔记本方案。

这条路线保留了你项目的长期目标，同时避免把“寻找训练状态”“学习战斗动作”“学习整局决策”混成一个无法诊断的系统。
