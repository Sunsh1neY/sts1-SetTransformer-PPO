## 4. 审计能否还原战斗入场状态

定义统一入场时点，区分战斗初始化之前与开战效果、初始抽牌之后，避免遗物触发两次。对每个字段记录来源位置、时点含义、重建规则和证据等级：直接记录、可靠推导、缺失/歧义。

至少审计：

- 当时牌组的具体卡实例、升级次数、添加/移除/变形/升级历史；不能直接使用最终 master_deck。
- 当前/最大 HP、层数、遭遇、进阶等级、游戏版本及影响入场的状态；逐层 HP 数组的前后时点须有证据。
- 当时持有的遗物、影响结算的计数和选定卡等参数；最终遗物列表不等于中途遗物状态。
- 药水槽位、容量、类型、获取/使用/丢弃和相关遗物影响；仅有获取记录不能推断完整库存。
- 开战效果和公开计数、隐藏 RNG/牌序。隐藏状态若只能重新采样，显式声明，不能宣称精确复盘。
- 旧版本与锁定后端的相关机制差异。匹配版本标签不足以证明机制一致；未知差异不当作已验证。

用真实样本给出逐字段证据。可见关键字段不确定的场景不得纳入正式候选；不得补默认值、删除内容或把历史动作送入 PPO on-policy minibatch。

建立机器可读场景清单和排除清单，区分“初态可重建但后端待支持”“当前已支持”“不可重建”。登记初态来源、原始 run 标识、文件哈希、难度、版本与各依赖。不要把 M3 才能支持的候选写成今天可运行。

## 5. 完成下一阶段可实施的契约

基于样本和锁定后端调用链，形成新的正式候选契约文档；保留旧人工诊断文档的历史身份。契约必须给出具体字段、类型、枚举/ID、容量、版本和动作编号规则，不能只写“后续扩展”。

- reset：显式输入场景及环境复跑 seed，明确定义遗物、药水、卡牌与入场状态如何注入，校验失败如何报告。
- 观测：列出玩家可见且影响决策的新增信息；遗物计数、药水槽位、活动状态和卡牌动态值不可遗漏。seed、RNG、隐藏牌序不进模型。
- 动作：为新环境设计五目标寻址与药水动作；需要二次选择的内容必须有完整语法才可列为批准范围，否则明确延期。不能让后端代替玩家选择。无目标与敌人0在语义上区分。
- 容量：手牌、敌人目标、牌堆和药水分别证明；覆盖重复生成及分裂/召唤，不能把初始牌数当全过程上界，也不能把任意大数组当证明。若使用外部步数限制建立界限，明确其截断、自举与记录语义，不得伪装为游戏失败。
- 迁移：集中声明 schema、registry、动作和序列化版本，shape 从契约派生；列出 C++、wrapper、模型头、Agent/runner、checkpoint 和轨迹的联动修改位置。旧 minimal-v1 原样独立，不兼容加载明确拒绝。
- 划分：按整局、重复记录和重复 seed 的关联组划分，再生成战斗场景；同源变体同组。固定划分规则和版本，验证无交叉。eval_seeds.json 不变，训练与评估环境 seed 仍遵守既有范围；历史 source seed 与模拟器复跑 seed 分开。

形成分批支持矩阵：卡牌/升级、遗物、药水、难度和遭遇的具体范围、依赖、源码入口、所需测试及对应真实候选数。保留 M3 的30–40类卡与 M4 约十种普通遭遇加三个精英目标，不为凑数静默降标。首批可以较小，但必须指出达到整体目标还差什么。
